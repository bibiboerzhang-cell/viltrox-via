## 执行摘要

**这是什么**:一套自托管的 KOL 营销智能操作系统——从"关键词发现创作者"到"视频逐帧深度分析"到"推荐-认领-内容-订单归因"的端到端闭环,服务 Viltrox 镜头业务。

**五个最重要的结论**:

1. **智能呈三段式,核心是确定性**:打分核心是受红线冻结的规则策略(rule_v0);LLM 全部被推到外围做"证据生产"(视频 6 层深析、受众推断、情感)与"草案生成"(5 个 skill);学习不改模型参数,走"特征快照→业务结果回流→反馈调权"的数据闭环。这个结构恰与 2026 年业界从"自由 agent"回摆到"确定性 workflow"的共识同向。
2. **数据流的腰部极窄且这是设计**:全系统异步工作共用一张 `apify_jobs` 队列表 + 一个串行 worker,预算闸与成本记账在此统一收口——利于审计,也是已知单点。
3. **工程纪律是最大长板**:每一处 LLM 出口都有四层预算闸 + rule 兜底 + 微美元记账;幂等设计贯穿(分析缓存三元键/评论去重/记账 14 天去重);哨兵十项日检 + 双指纹发布门禁。业界对照结论:单点算法均非 SOTA,但"每层都带预算闸、账本、降级与人审"的能力是多数用框架的团队反而没有的。
4. **已建成未接线三处(本报告实查发现)**:平台层 ModelRouter(测试全绿、生产零调用点)、DSAR 级联删除(模块存在、无 API 路由调用)、驾照分级自治(设计在作战地图廿一节,`autonomy_license.py` 全仓不存在)。
5. **代码层本地与线上已收敛**:7-03 三波施工(28+ 提交)全部部署;本地领先部分几乎全是作战地图文档提交。真正的瓶颈已不在代码,而在真实数据流量(Shopify webhook、Amazon 三件套、员工实测)。

### 2. 启动流(main.py lifespan)

`app/main.py:553` `lifespan` 顺序:① `init_db_runtime()`(`db/connection.py:568`)——Postgres 模式下开池→**自动 apply 迁移**(`_run_postgres_migrations`)→bootstrap 默认 admin→跑 runtime seeder;② 条件启动本地编排器(`ENABLE_LOCAL_ORCHESTRATOR`,默认仅 `APP_ROLE=all`+无 Redis+非生产)与 Playwright 浏览器;③ `build_job_queue`(有 `REDIS_URL` 用 RedisJobQueue,生产强制要求);④ `ENABLE_SCHEDULER`(默认仅 `APP_ROLE=all` 为 1,`core/config.py:372`)时 `start_scheduler()`;⑤ `ENABLE_UPLOAD_CLEANUP` 起 24h 清理循环。关停按相反顺序收尾并 `close_db_runtime()`。

Router 注册为静态白名单式:先挂公共 router(auth/uploads/webhook 等),再按 `APP_ROLE` 分面——`IS_PUBLIC_APP` 挂 creator/leaderboard/sse 等,`IS_ADMIN_APP` 挂全部 admin+vkpi 系列(共 76 次 `include_router`)。中间件栈 7 层:CSRF origin 校验、admin RBAC(按 URL 前缀映射权限键,`_admin_permission_for_request`)、**db_scope_middleware**(每请求一个 `db_connection_scope()`,请求结束归还连接并顺带写敏感操作审计)、admin 安全头、请求指标、安全响应头(CSP/HSTS)、`/api/marketing`→`/api/admin/vkpi` 别名重写。`/health` 返回 build SHA 对齐、worker 心跳判活、迁移水位(`_trust_db_migration_max` 读 `schema_migrations` 实际已应用集而非代码声明尾,防假阳)。

### 3. Worker 模型(apify_jobs 队列)

**表结构**:`migrations/095_apify_jobs.sql` 建表(id/job_type/payload JSONB/status/attempts/last_error/created_at/updated_at),后续迁移演进:097 加 `blocked` 状态、105 加 `next_retry_at`+`last_error_category`、112 加 `started_at`、170 加显式租约列 `lease_owner`/`lease_expires_at`+幂等预留列(idempotency_key/input_hash/output_hash)、201 加 `triage` 状态——status 枚举现为 queued/running/done/failed/blocked/triage。

**单进程串行 + 三档优先抢单**:`run_worker()`(apify_jobs_worker.py:750)外层 DB 断线重连循环、内层单连接 poll(默认 2s),一次只 claim 一条、串行处理。`_claim_job`(:381)用 `FOR UPDATE SKIP LOCKED LIMIT 1`,ORDER BY 三档:tier0=单条交互(无 batch 标记,含链式 followup)> tier1=`payload.batch='on_demand_batch'`(用户"分析全部")> tier2=`batch IN ('recent','remaining')`(系统批量),配套 partial 函数索引(迁移 156,表达式与 ORDER BY 逐字一致),解决批量压死交互的队头阻塞。

**租约**:claim 时写 `lease_owner=worker名:pid`、`lease_expires_at=NOW()+STALE_RECLAIM_SECONDS`(默认 10 分钟);处理中由心跳线程(`_heartbeat_running_job`)持续续租+刷 updated_at;`_reclaim_stale_running_jobs`(maintenance 模块,每 60s)回收僵尸 running。worker 每轮 poll(含空闲)UPSERT `vkpi_worker_heartbeat`,供 /health 判活。

**错误分类与重试**:`_error_category`(helpers.py:59)把错误文本归入约 10 个细类(provider_pressure/timeout/media_resolve/download/content_restricted/content_blocked/content_unavailable/permanent/stale_running/code_error/unknown);`_failure_disposition`(:207)三分:可重试类(天气问题)→ 重新 queued+指数退避(provider_pressure 专属 5 次预算,其余默认 2 次 `MAX_JOB_ATTEMPTS`);确定性死类 → `status='triage'` 待人工;可重试类耗尽预算也汇入 triage(而非死在 failed 池);仅 unknown 保守落 failed。`_fail_job`(:575)对 attempts 行加 `FOR UPDATE` 后原子分流。LLM 类 job 另有 advisory lock 目标去重、LLM 并发槽(默认 2)、Gemini QPS 限速与预算预检(超 cap 直接 `blocked:budget_guard_blocked`)。

### 4. 调度(APScheduler)

`services/scheduler/jobs.py` 的 `start_scheduler()` 共 **48 处 `add_job`**(2 处注册期条件门:B&H 周抓需 `BH_SNAPSHOT_ENABLED`、Via 学习需 `VIA_ENABLE_DAILY_LEARNING`;其余始终注册,多数在 job 体内由 `scheduler_tasks` 注册表 enabled 开关 config-gate)。代表 10 个:① `vkpi_morning_sync`(中国 08:00 每日 KOL/渠道/产品同步);② `vkpi_recommendation_refresh`(04:00 推荐重算,只读 fit);③ `vkpi_recommendation_outcomes`+`vkpi_outcomes_refresh`(学习闭环 outcome 回填);④ `vkpi_fulfillment_sweep`(05:10 durable 履约 sweep)及 fulfillment_delivered/content/window_backfill/due_scan 履约簇;⑤ `vkpi_agent_cycle`(05:30 Agent 建议链);⑥ `vkpi_official_daily_report_asia/americas`(官号日报双时区两轮);⑦ `llm_batch_poll`(每 10 分钟回收 Anthropic Batch)+`vkpi_content_fit_batch_refresh`(过夜批提交);⑧ `worker_lease_expire_stale`(每 5 分钟租约清扫)+`ops_threshold_alerts`(15 分钟阈值告警);⑨ `vkpi_health_sentinel`(09:30 十项黄金链路只读日检)+`vkpi_cost_snapshot`(08:20 成本快照);⑩ `vkpi_goaffpro_metrics_sync`(每 5 分钟联盟指标缓存)。所有 job 均 `max_instances=1, coalesce=True`。除随 web 进程的 `ENABLE_SCHEDULER` 外,另有独立常驻入口 `scripts/scheduler_daemon.py`(launchd `com.viltrox.vkpi-scheduler` 拉起)。

### 5. DB 层

**compat 双方言**:`db/connection.py` 保留 sqlite 风格 SQL 表面(`?` 占位、`lastrowid`、`PRAGMA table_info`、sqlite_master 查询),生产流量走池化 Postgres。`connection_sql_translation.py` 做逐字符状态机翻译:`translate_sql_placeholders` 把字符串字面量外的 `?` 换成 `%s`(引号内的 `?` 不动——这正是历史上「迁移注释里 ASCII ? 当占位符炸 apply」陷阱的边界);另翻译 `INSERT OR IGNORE`→`ON CONFLICT DO NOTHING`、PRAGMA→information_schema、strftime/GROUP_CONCAT/datetime('now')→PG 等价物。`PostgresCompatCursor/CompatRow` 提供 sqlite3.Row 语义,`_normalize_pg_value` 把 bool 归一成 int(BOOLEAN 读回 1/0 的行为根源)、datetime 归一成 UTC 字符串。

**迁移序列**:`_POSTGRES_MIGRATION_SEQUENCE`(connection.py:53)硬编码 **210 个** .sql 文件名(003→209,`migrations/` 目录实存 341 个含 _down 回滚件);启动时 `_run_postgres_migrations`(:613)建 `schema_migrations` 表→`pg_advisory_xact_lock` 防并发双跑→按序对未应用项 `read_text()` 执行并登记,缺文件直接 RuntimeError 拒启。

**pool 自愈**:`_get_pg_pool`(:369)双重检查锁的全局 ConnectionPool(psycopg_pool,PgBouncer 模式禁 prepared statements);2026-07-02 加自愈——发现池 `closed` 即丢弃重建,根治「deep_crawl 收尾关全局池后同进程后续 job 全灭 PoolClosed」。连接获取三级:请求作用域 `_ScopedConnectionHandle`(ContextVar,懒建、请求毕归还)→ 线程局部 → `open_standalone_conn` 独立生命周期。

**红线说明**:队列/租约类迁移(156/170)注释均显式声明零触碰 KOL 评分域;`viltrox_fit_score` 为 KOL 评分存储列、`rule_v0` 为规则版评分器,二者属变更红线,本章仅确认其存在与角色,不涉内部逻辑。

### 二、KOL 评分层

**rule_v0(红线区,只述角色)**:系统唯一在用的 KOL 打分策略,实现于 `backend/app/domains/scoring/rule_v0.py`,以 `version="rule_v0"` 注册进 `scoring/base.py` 的 `ScoringRegistry`(策略模式,`ScoringResult` 带 score/breakdown/strengths/concerns)。它是确定性、零 LLM、可复算的规则策略;其产出写入 `viltrox_fit_score` 的路径受红线保护——全仓大量模块在 docstring 中显式声明"绝不写 viltrox_fit_score"(如 `url_deep_crawl_execute_profile_videos.py`、`outreach_pack.py`、`pool_inflation.py`),写点唯一且有写后比分回滚护栏(`docs/KOL-Pool-顶配方案-20260613.md` 红线1)。实际调用链:`pool_enrich.py:151`(富化适配器)→ 入口为 API `vkpi_kol_pool.py:621` 手动富化与 `sync/daily_sync.py:354` 每日同步。另注意 `llm_gateway` 里的 "rule_v0" 是同名但不同物——那是"不烧 LLM 的规则兜底 provider"标签(见第五节)。

**独立 11 维(P0-2 方案)**:`eleven_dimensions.py` 自述为 "Rule-only 11-dimension KOL profile scoring, v2.1 dry-run layer"。输入 kol_pool_id(读缓存的 Pool 行+帖子+竞品检测器),输出 4 个 block——`compute_block1_content`(内容)/`block2_performance`(表现)/`block3_business`(商业)/`block4_specialty`(专长)——由 `compose_dimensions_11()` 合成 11 维,每维带 0-100 分与置信度,产品契合用 SKU 关键词表(`PRODUCT_FIT_KEYWORDS`)与行业聚类(`industry_clusters.json`)。这正是顶配方案对 P0-2 的裁决落地:所有质量/产品线维度一律走**独立列/影子分**,严禁引入第二条写 fit_score 的路径(docs/KOL-Pool-顶配方案-20260613.md:207)。消费方为情报卡(`intelligence_card_helpers.py:141`)、Pool 详情(`pool.py:498`)与内容契合分析。

### 三、召回与搜索层

**向量召回**:`profile_recall.py` 的 `recall_kol_profiles()`。输入 query 文本/SKU + 配额参数,输出 creator/reviewer 双桶排序候选。链路:`_embed_query()` 用 OpenAI `text-embedding-3-small`(EMBEDDING_MODEL,profile_recall.py:17;1536 维)嵌入,调用前有 `check_budget("provider:openai")` 硬闸、调用后 `record_cost` 记账;`_search_qdrant()` 查 Qdrant(本地 `runtime/vkpi_qdrant` 或 QDRANT_URL);`_recall_rank_score()`(profile_recall.py:670-680)按 `vector_score×vector_weight + (type_score/100)×type_weight` 合成。**权重定义点有两处**:函数签名默认 0.85/0.15(profile_recall.py:768-769),而发现层 API 默认 0.7/0.3(`profile_discovery.py:429-430`、`profile_discovery_queue.py:299-300`)——线上智能发现走 0.7/0.3 口径。向量库不可用时优雅降级为空召回(不 503)。展示层另有二段增强(采纳回流上浮 + LLM 头部 rerank),只动 `display_rank_score` 不动召回分。

**CJK 分词**:`domains/search/natural_search.py` `_tokens()`(诊断 P1-6)。中文整串在无分词时会被当 1 个 token,`LIKE '%整句%'` 永不命中导致库内 0 召回;修复为对长度>2 的 CJK token 补全部 2-gram 子串,各 token 在 WHERE 里 OR 合并广召回,精排交 `_score_row`(注释明示 jieba/PG 全文为后续专项)。

**地区排除口径**:`profile_recall.py:394-411`,P0-6 裁决——只按地区 {CN/HK/TW} 排除(正则匹配中文地名 中国/大陆/香港/台湾/Hong Kong/Taiwan/China + ISO 码集合 {CN,HK,TW,CHINA}),country 为空放行;旧"汉字判据 `_looks_chinese`"已整体删除(误杀海外中文博主)。在召回主循环对每个命中行生效(`exclude_chinese=True` 默认)。

**persona 相关度**:`profile_recall_relevance.py` `_relevance_signals()`。输入候选行+证据+本次 query 是否"视频向"(`_is_video_leaning_product` 按产品线白名单/人群词判定),输出 `(display_relevance_adjust, relevance_flags, note_parts, tier_hint)`:①视频向产品×纯平面摄影候选 -0.12 展示分并标"平面为主";②品牌合作≥6 条标"合作过载" -0.04;③高粉饱和大号降权、上升期小号加 boost(新人优先)。另有 `WHY_FIT_RULES` 规则桥:11 条(人群侧词, KOL 画像信号词, 人话短语)三元组,双侧命中才产出 why-fit 理由。文件头红线明示:全部只进独立展示字段,绝不并入任何评分。

### 四、受众估算 ensemble_v1

`audience_stats.py`(METHOD="ensemble_v1",audience_stats.py:40)。入口 `refresh_audience_stats(kol_pool_id)`(:1424):**抽样→推断→聚合→一次写库**。分层法(全部经文件头 docstring + 函数体核实):

- **评论者抽样**:YouTube 走 Data API `commentThreads`+`channels.list` 批量(`sample_youtube_commenters`,免费额度顺带拿自报 country/bio/订阅数/频道创建时间);IG/TT 复用库内 `vkpi_comments`(`sample_local_commenters`),不足 30 条(MIN_LOCAL_COMMENTS)先入队抓评论、不出低质画像。
- **国家三层信号逐层降置信**:自报 country 置信 0.9 > 人名词表国籍猜 0.4 > 评论语言推市场 0.3(`audience_language.detect_lang` + `LANG_TO_MARKETS`)。性别用约 500×2 人名词表,置信 0.8,未知留空不猜。
- **年龄三路融合(v2)**:A=Gemini 批推(经 llm_gateway,批 50、单次刷新最多 4 批的成本闸)> B=m3inference 可选依赖 > C=频道注册时间弱先验(conf 0.3);`_fuse_age`(:715)按置信加权投票,赢家桶内 noisy-or 相互印证抬置信、有分歧再乘份额降置信。
- **置信折扣与收缩**:整体 confidence = min(0.9, 0.15 + 0.45×样本量因子 + 0.3×自报占比 + 0.1×语言可判占比)(:1229,IG/TT 无自报路天然降档);聚合后做经验贝叶斯收缩,prior=同垂类其它 KOL 已有画像均值,tau=50(`_apply_shrinkage`,:1168)。
- 推断结果落 `vkpi_commenter_profiles` 缓存跨 KOL 复用;评论情报(`comment_intel.py`,购买意向/品牌提及/铁粉,纯词表零成本)并入同一 `audience_estimated_json`。红线:明示 method/置信度,绝不冒充官方数据、绝不写 fit。

### 五、视频深析 final_v1

- **主分析器**:`gemini_video.py` `analyze_local_video_with_gemini(schema_key="final_v1")`。输入本地视频文件+标题+账号上下文+字幕+真实播放数据,Gemini(默认链 `gemini-3-flash-preview`→`gemini-2.5-flash`)全视频理解,输出**固定 6 层 JSON**(`gemini_video_prompts.py:135-240` 核实):layer1 画面内容(场景时间线/产品出镜/品牌露出/竞品/制作观察)、layer2 观众情绪模拟(心动分/购买欲/广告疲劳,必须与真实播放数据对照指出矛盾)、layer3 三价值拆分(渠道价值/素材买断价值/产品证明价值)、layer4 美感归因(镜头光学 vs 灯光/LUT/后期/模特,share_pct 估计)、layer5 可执行建议(合作/买断/下轮 brief/索取清单/预算动作)、layer6 风险旗标+六项分数+final_verdict。每个分数强制带 confidence+evidence,评分锚点与"证据不足给 null"写死在 static prompt;static prompt 走 Gemini 上下文缓存省钱(`_final_v1_cache_config`)。调用方:任务 worker `apify_jobs_worker_media.py:166`。
- **keyframe QA**:`gemini_video_keyframes.py:98` `analyze_final_v1_keyframe_qa()`——把关键帧 JPG+已产出的 final_v1 结果喂给 `gemini-3.1-pro-preview`,只做事实复核不重生成:五项 checks(product_identity/brand_exposure/competitor_context/inscription_or_model_text/title_image_consistency,pass/warn/fail/unknown)+qa_pass+confidence。调用方 `apify_jobs_worker_gemini_judges.py:126`。
- **落库投影**:`final_v1_extract.py` 只读 `vkpi_analysis_cache` 提取 final_v1/QA 两个 derive_method,写独立表 `vkpi_kol_llm_deep_analysis_results`(即 `llm_dimensions_11` 存放处),文件头明示绝不更新 Pool 评分字段、不调 LLM。另注:prompt 里的"11维理念"作为规则 F 融入 6 层框架,与第二节账号侧独立 11 维是两套并行产物。

### 六、智能层(Marketing Brain)

**5 个 Skill**(`marketing_brain/skills/`,统一契约 `run(input, *, model_fn=None, record=True)`,model_fn 默认 None=纯规则零 LLM,record 落 `vkpi_skill_runs` 账本;全部声明零写 fit):
1. `creator_match`:输入 {product|sku, market, budget?} → 复用 `recommendations.new_launch_match.build_new_launch_match_preview` 确定性匹配,输出 recommendations[{kol_pool_id, handle, fit_reason, risk, est_cost_cents, evidence_refs}]+rationale。
2. `brief_generate_v1`:输入 {kol_pool_id, product, angle?} → 复用外联档案+SOW 模板,输出 {brief:{hook, talking_points[], do[], dont[], deliverables[]}, editable:true},永远可人审改。
3. `campaign_plan`:输入 {product, market, budget_cents, goal} → 复用 market_brain 日简报+Pool 候选,输出 {plan:{creator_mix[], budget_allocation[], timeline[], content_angles[]}, risks[]}。
4. `content_score`:输入 analysis_cache_ref/video_url → 只读 final_v1 缓存投影成打分 schema,绝不重跑视频分析。
5. `roi_review`:输入 {project_id|kol_pool_id, window?} → 复用 `aggregate_project_metrics`/`get_kol_roi_summary` 出 ROI+outcome_labels+next_action,无真数据诚实返回 missing_data。

**skill_orchestrator**(`skill_orchestrator.py`):`plan_skills(goal, context)` 是**确定性规划**——纯关键词+实体信号规则选 skill 与 input(`_select_skills`,:148:有 product→creator_match、有 budget→campaign_plan、有 kol_pool_id+话术词→brief、有 target_id→content_score、有 project_id+复盘词→roi_review,兜底 creator_match),零 LLM 可单测;`orchestrate_skills` 经 `skill_registry.dispatch_skill` 真调用并落账本。安全闸:dry_run 默认 True(model_fn=None 绝不真烧)、`budget_guard.check_budget("marketing_brain_skill")` 不过标 budget_blocked、总开关 `VKPI_SKILL_ORCHESTRATION` 默认开。调用方:HTTP `vkpi_agents.py:341` 与调度器 `scheduler/jobs.py` 的 `vkpi_skill_auto_orchestrate` 定时任务。

**ModelRouter**(`platform/models/router.py`):纯确定性选型函数——①按质量/速度/上下文下限与成本上限硬过滤模型注册表(`quality_policy.py`/`cost_policy.py` 提供纯函数门槛与打分);②幸存者按 `w_q×quality + w_c×cost + w_s×speed` 归一化加权打分(默认权重 0.5/0.3/0.2,RouteRequest 可调);③按分数→质量→更廉价→稳定 key 排序,榜首为 primary、其余为 fallback 链;④全部不过滤则降级最廉价/本地模型,永不 raise。真实调用委托 `llm_gateway.invoke`(`route_and_invoke`),自身不重写传输;另带 key 池轮换选择(`select_key_for`)。**核实:生产代码目前无调用点,仅 `tests/test_model_router.py`/`test_key_pool_router.py` 覆盖**——已建成待接线,与账本"skills 未接 orchestrator"一致。

**llm_gateway**(`platform/llm_gateway.py`):全系统 LLM 文本调用统一入口 `invoke()`。**兜底链** `PROVIDER_ORDER = ("openai", "google", "anthropic", "rule_v0")`(:40):逐 provider 尝试,未配置/预算拦/调用失败则顺延,全灭时落 `_rule_fallback`(:403,status="fallback_to_rule",provider 标 "rule_v0",零计费不阻断上层)。**预算闸四层 scope**(`_budget_scopes_for_provider`,:260-262,经 `budget_guard.check_budget_scopes` 联合校验):① `monthly_total` 月度总额;② `single_call` 单次调用上限;③ `provider:<openai|gemini|claude>` 单供应商额度;④ `cost_scope` 功能位口径(cost_tag 或 `cron:<purpose>`)。护栏采用 require_configured=False 口径:只对真配了 caps 行的 scope 硬拦(provider_preflight 拦下即记零成本台账再 fallback),无配额行的功能 scope 放行防误杀;另有两道 record-only 预检(cost_scope 硬停探测与月度预算探测)只入台账告警。每次成功调用按 micro-USD 精度记账进用量台账。

### 七、学习层

- **feature_snapshot**:`recommendations/new_launch_match.py:105-155` 在生成每条推荐时构造特征快照与打分拆解,整批 commit 后经 `outcomes.ensure_outcome()`(outcomes.py:35)幂等落 `vkpi_recommendation_outcomes`(含 feature_snapshot_json/scoring_breakdown_json/model_version="rule_v0"/display_position/display_context)——这是"当时看到什么、为何这么排"的留痕底座。
- **outcomes 回流**:`outcomes.py` 定义 9 个漏斗节点(shortlisted→rejected→claimed→project_created→outreach_sent→reply_received→agreement_reached→content_published→order_attributed,NODE_COLUMNS :13),`record()` 单点打标;`refresh_open_outcomes()`(:412)批量扫近 N 条推荐,从真实业务行(认领/消息/内容/销售净额,退款计净)自动促升标签,挂在调度器每日 job(`scheduler/jobs_tasks.py:194`)。
- **反馈→打分**:真实操作写 `vkpi_recommendation_feedback`(`recommendations/actions.py`,收藏映射 shortlist 等 `_POOL_ACTION_FEEDBACK` 词表,幂等防重复点击);`recommendation_agent.py:12` 的 `FEEDBACK_SCORE`(shortlist +8 / claim +6 / create_project +8 / reject -20 / snooze -8 等)在 `recommendation_use_case.py:131` 按类型×min(3,次数) 累加,总调整夹在 [-35,+24],作用于下一轮推荐排序(不触 fit 存储列)。另有 `compute_next_recommendation_weight`(roi_aggregate.py:147)把漏斗成功度(claimed 0.2/agreed 0.3/published 0.5)与 Agent 结果回写成功率按 0.6/0.4 融合成 0-1 独立展示权重。
- **training_export**:`training_export.py` `export_training_dataset(date_from, date_to)` 把推荐行+outcome 联表逐条导出 JSONL 至 `runtime/vkpi_training_exports/train-<hex>.jsonl` 并登记 `vkpi_training_exports` 表(status/row_count)——为"未来 ML 打分器"备训练集,当前系统未训练任何模型。
- **Evals 框架(两套互补)**:①`marketing_brain/evals.py` 离线样本级——`run_eval(skill_fn, cases)` 用可注入 metric 打 [0,1] 分,内置 `exact_match_metric` 与 `set_overlap_metric`(Jaccard,适配 creator_match 候选集),单条异常记 miss 不断批,汇总命中率/平均分;②`domains/platform/evals.py` 在线业务断言套件——跑真系统函数并断言关键行为(推荐不碰 fit、召回有结果、权重有界、事件总线往返、预测诚实),结果持久化,升级后跑一遍看分数是否退化。HTTP 入口 `vkpi_agents.py /skills/evals`。

### 八、附:其余在库智能组件(简列)

`smart_query_planner.py`(自然语言需求→有界搜索计划,LLM-backed、provider 不可用退确定性规则计划,不写评分)、`comments/sentiment.py`(P1.4 多维情感:sentiment/emotion,经 llm_gateway)、`pool_inflation.py`(P0-3 假粉规则离群检测,只写 suspect_inflation 独立列)、`comment_intel.py`(纯词表评论情报:购买意向/品牌提及/铁粉,零成本)、`competitor_detector.py`(竞品暴露规则检测,喂给 11 维 block)。以上均在各自文件头声明零触 fit 红线。

### 结论

系统的"智能"呈清晰三段式:**打分核心是受红线冻结的确定性规则(rule_v0)**,LLM 全部被推到外围做"证据生产"(视频 6 层深析、受众推断、情感、query 规划)与"草案生成"(5 个 skill),且每一处 LLM 出口都有同一套四层预算闸+rule 兜底;学习不改模型参数,而是走"特征快照→业务结果回流→反馈调权"的数据闭环,并已备好 training_export 与双 evals 框架作为未来换模型的地基。已建成未接线的部分只有一处:平台层 ModelRouter(测试全绿、生产零调用点)。

### 四、结构性观察

1. **单队列单闸门**:所有异步工作(搜索、视频深析、评论采集、合同抽取、物流同步)共用 `apify_jobs` 一张队列表和一个 worker 进程,预算闸(budget_guard)与记账(ai_cost_ledger)在 worker 内统一收口——数据流的"腰部"极窄,利于审计但也是单点。
2. **幂等设计贯穿**:analysis_cache 的三元唯一键、comments 的平台+外部 ID 约束、record_apify_run 的 14 天 run_id 去重、ensure_outcome 的有行即跳,使重试与重放不产生脏数据。
3. **学习链只促升不臆造**:`refresh_business_outcome` 的标签全部来自已存在的真实业务行(projects/messages/claims/sales_attributions),代码内明确注释"never fabricates platform data",这是该链可信度的根基;其瓶颈在真实业务事件的水量而非代码。

# 第四章 前端架构

### 1. 总体结构:单壳单路由,三层分工

前端位于 `frontend/`,技术栈为 React 18.2 + TypeScript 5.5(strict 模式)+ Vite 5 + Tailwind 3,路由用 react-router-dom 6,动效 framer-motion,图标 lucide-react,测试 Vitest + Testing Library(`frontend/package.json`)。源码共 352 个 .tsx + 265 个 .ts 文件,非测试 .tsx 总量约 6.6 万行。

**启动链**:`src/main.tsx` → `AppProviders`(仅包一层 `AuthProvider`,`src/app/providers/AppProviders.tsx`)→ `AppRoot`(`RouterProvider`)。

**路由层刻意做薄**(`src/app/router.tsx`):`createBrowserRouter` 只有 4 条真实路由——`/`(AdminRoute,唯一业务入口)、`/login`、`/activate`、`/reset`,其余 `/admin/*`、`/react/*`、`*` 全部 `Navigate` 重定向回根。每条路由都是 `lazy()` + `Suspense` + 统一 `RouteErrorBoundary`。整个产品是**单路由单页应用**,页面切换不走 URL 路由,而走内部导航状态(hash + localStorage)。

**鉴权门**(`src/routes/admin/AdminRoute.tsx`):按 `useAuth` 的三态(loading/guest/authenticated)分别渲染"恢复会话卡"、登录页、或权限校验。`hasMarketingPermission()` 检查 `is_owner` 或 `permissions.vkpi/marketing ∈ {read,write,admin}`,不通过则渲染"访问被拒绝"卡片;通过后进入 `VkpiTab`。

**三层分工**:

| 层 | 位置 | 职责 |
|---|---|---|
| services | `src/services/vkpi/`(53 个 API 模块)+ `src/lib/api.ts` | 纯 HTTP 封装,零 UI |
| domains | `src/domains/`(16 个业务域,dashboard 最大 13 文件) | 业务模型/格式化/契约;README 明确"新功能代码落这里,页面壳保持薄" |
| components | `src/components/vkpi/` | 页面与组件,cockpit 为主壳 |

**services 层模式**:所有请求收敛到 `apiFetch<T>()`(`src/lib/api.ts`,86 行起):默认超时 20 秒(`DEFAULT_API_TIMEOUT_MS = 20000`),每调用可传 `timeoutMs` 覆盖;AbortController 双源中止(外部 signal + 超时),超时抛中文错误"请求超时:{ms}ms";统一注入 Bearer token 与 `X-Requested-With`;非 2xx 统一抛 `ApiResponseError`(逐层提取 `detail.reason/message` 生成可读文案)。`src/services/http.ts` 只是对 `lib/api.ts` 的 re-export,保证全站单一 HTTP 入口。

## 5. 测试与工程

- **测试规模**:`tests/` 共 **172 个 Python 文件、22,826 行**(`pytest.ini`:`testpaths=tests`,`pythonpath=backend`,`--strict-markers`),覆盖 worker 契约、成本记账、RBAC 映射、失败池 triage、迁移 manifest、健康对齐门禁等。
- **make verify**:存在且是薄入口,真逻辑在 `scripts/verify.sh`,串 **6 步**、任一失败整体非 0:① 后端 pytest(.venv 解释器)② 前端 `tsc --noEmit` ③ 前端 `npm run build` ④ `check_repo_hardening.py --strict` ⑤ 红线 grep——`viltrox_fit_score`(存储列)的 DB 写点只允许出现在白名单三个文件,越界即 fail ⑥ 运行态 sha 对齐——本地 8102 服务在跑则强校验 `/health` 的 `trust.sha_aligned=true`,没起则跳过不破静态 CI。
- **Docker**:`backend/Dockerfile`(python:3.13-slim,uvicorn 8102,锁版本 requirements)与 `frontend/Dockerfile` 均存在;`docker-compose.yml` 编排 postgres:16(宿主 54329)+ redis(6380)+ backend(8102)+ frontend(5173),`docker compose up` 可复现本地验证环境,DB/Redis 在 compose 内强制指向服务名避免被本地守门逻辑改写。

**小结**:这一章的工程底盘特点是「极简线上 + 厚防护层」——线上只有一进程 Web、一进程 worker、两个 timer,但哨兵日检、双账本记账、双指纹对齐、多级预算闸、三层缓存和四级 RBAC 全部长在代码里且大多有测试锚定;当前最值得点名的缺口是 DSAR 删除能力未接线成 API,以及 Apify 记账只覆盖内部发起的 run。

# 第八章 业界与 GitHub 对照

本章将本仓库(HEAD 3ee7d985)四个技术维度与 2026 年业界主流开源方案逐一对照。所有"我们的实现"均经真实代码核实(给出文件与函数);业界侧引用具体开源项目与公开资料。判词按"领先 / 合理 / 落后"三档,不吹不缩。

### 一、Agent 编排:确定性规划 vs LLM 自由编排

**业界 2026 现状。** 三大主流框架格局已定:LangGraph(图状态机,生产成熟度最高,内置 checkpoint/时间旅行调试/human-in-the-loop/持久执行)、CrewAI(角色制,上手最快)、AutoGen(微软已转入维护模式,并入 Microsoft Agent Framework,新项目不建议采用)。同时业界方法论出现明确回摆:Anthropic《Building Effective Agents》与社区"12-Factor Agents"共识都指出——**生产环境成功的系统多数不是自由编排的 agent,而是"确定性代码路径 + 关键节点放置 LLM 决策"的 workflow**;AutoGen 式多 agent 对话单任务动辄 20+ 次 LLM 调用,成本与不可预测性是主要生产障碍。

**我们的实现(已核实)。** `backend/app/domains/marketing_brain/skill_orchestrator.py`:`plan_skills`/`_select_skills` 用目标关键词 + context 实体信号做**确定性 skill 选择(零 LLM、可单测)**;`orchestrate_skills` 带三重闸——`dry_run` 默认 True 强制 `model_fn=None`(不烧 LLM)、预算闸 `budget_guard.check_budget("marketing_brain_skill")`、env 总闸 `VKPI_SKILL_ORCHESTRATION`。`skill_registry.py` 的 `dispatch_skill` 按 canonical 名分发 5 个 skill,每次运行经 `record_skill_run` 落 `vkpi_skill_runs`(迁移 199),`skill_acceptance_stats` 聚合采纳率/成本/延迟——即**每个 skill 有运行账本和被人采纳与否的统计**。上层 `agents/orchestrator.py` 是 PLAN-ONLY,`tool_registry.py` 中写库/烧 LLM 的工具一律 `requires_approval=True` 走 Action Inbox 人审。配套还有 `evals.py`(可注入 metric 的离线评测)与 `ontology.py`(纯类型营销本体)。**驾照制度(L0-L3 按预测命中率升降级的"挣来的自治")目前仅是设计**,见 `docs/vkpi_作战地图_总线路图_2026-07-03.md` §廿一,`autonomy_license.py` 尚不存在(grep 全 backend 无实现)。

| 项 | 业界(LangGraph 代表) | 我们 |
|---|---|---|
| 编排范式 | 图状态机/角色对话,LLM 可自由决策 | 确定性关键词规划,LLM 仅在 skill 内部按需使用 |
| 状态与恢复 | checkpoint、持久执行、时间旅行调试 | 无 durable execution,只有运行账本 |
| 人审/安全闸 | HITL 需自行编排 | requires_approval + Action Inbox + 预算闸 + dry_run 内建 |
| 效果度量 | LangSmith 等外部可观测生态 | vkpi_skill_runs 采纳率/成本/延迟内建落库 |

**判词:合理,局部理念领先,编排表达力落后。** 走"确定性 workflow + 人审闸"与 Anthropic/12-Factor 的 2026 共识同向,且"skill 运行账本 + 采纳率统计"是很多用框架的团队反而没有的闭环;但对比 LangGraph 缺多步状态机、断点恢复与可观测生态,规划器是关键词规则、表达力有限。驾照分级自治的设计理念在业界尚无主流开源对标(属前沿),但**未落码就只是纸面领先**,不计入实绩。

### 二、LLM 工程:gateway/router

**业界 2026 现状。** LiteLLM(BerriAI,51k+ stars,Stripe/Netflix 采用)已成事实标准:统一 100+ 供应商、成本追踪、virtual key、负载均衡、fallback、缓存、管理 UI。路由智能方向的代表是 lm-sys 的 RouteLLM:**训练出来的 learned router** 按 query 难度分流大小模型,公开口径可省 40-85% 成本保 95%+ 质量;托管侧有 OpenRouter。

**我们的实现(已核实)。** `backend/app/platform/llm_gateway.py`(739 行):`invoke()` 统一入口,`PROVIDER_ORDER=(openai, google, anthropic, rule_v0)` 供应商链式 fallback——其中 rule_v0 的角色是**零成本规则兜底 provider,保证外部 LLM 全不可达时链路不断**(其内部逻辑属红线不展开);预算体系四层 scope(monthly_total / single_call / provider / 按用途 cost_scope),逐调用落台账 `record_call`,默认月预算为 0(不显式配预算就不产生外部花费);`_pooled_api_key` 接 Fernet 加密的多账号 key 池。`platform/models/registry.py` 定义 5 个 `ModelSpec`(GPT/Gemini/Claude/Qwen/local_vllm),**`is_local` 槽位已预留本地自托管模型**;`platform/models/router.py` 的 `route()` 是纯函数确定性路由:quality/speed/context/cost 硬过滤 → 加权打分 → fallback 链 → 无候选时降级取最便宜可用(永不 raise);`route_and_invoke` 把传输完全委托给 llm_gateway,不重写任何 provider。省钱侧:`llm_batch.py` 接 Anthropic Message Batches(50% 折扣、仅云端提交),`gemini_video.py` 的 `_final_v1_cache_config` 做 Gemini 上下文缓存。

**判词:合理;通用性落后于 LiteLLM,路由智能落后于 RouteLLM,预算治理是独有长板。** 功能面上这是一个自研"小 LiteLLM"(多供应商 fallback、成本台账、key 池轮转、batch、缓存全有),存在一定重复造轮子;LiteLLM 的 100+ 供应商、virtual key、管理 UI 与社区维护我们没有。但两点买不来:一是预算闸与业务用途深度耦合(单调用/月度/供应商/用途四层 scope + 默认零预算的"不配不花钱"姿态),二是 rule_v0 兜底档让"LLM 不可用"成为降级而非故障。短板要如实讲:router 的 quality/speed 分是**手写启发式常数**(registry 注释自认 routing heuristics),对比 RouteLLM 的数据驱动路由差一代。

### 三、RAG/检索:hybrid search 与 rerank

**业界 2026 现状。** 标准检索栈已收敛为三段:**稀疏(BM25/SPLADE)与稠密向量并行召回 → RRF(k=60)按名次融合(公认优于线性加权)→ cross-encoder 对 top-100 重排**;Qdrant 官方教程即此模式(hybrid + late-interaction rerank)。BM25 层的价值在精确匹配长尾(型号/错误码类 query 纯向量常全灭)。

**我们的实现(已核实)。** `backend/app/domains/kol/profile_recall.py`:Qdrant collection `vkpi_kol_profile_index_v1`(支持远端 URL 或本地路径),OpenAI `text-embedding-3-small` 1536 维;`_embed_query` 调用前有预算硬闸、调用后记账;召回后按 creator/reviewer 分桶、`vector_score×w + type_rank×w` 排序;展示层二段增强——采纳回流 boost + `_llm_rerank_buckets`(经 llm_gateway,purpose=`vkpi_recall_rerank_v1`)做 **LLM 头部重排,只改 display_rank_score、原始分保留、diagnostics.display_rerank 留审计痕、失败静默降级**。文本搜索是另一条并联入口:`smart_query_planner.py` 用 LLM 规划检索词、`_fallback_plan` 规则兜底,并有 pool 兜底保证永不零结果。

**判词:合理偏落后。** 对标 2026 标准,缺三件:没有 BM25/稀疏索引并行召回,没有 RRF 分数融合(文本与向量是两条并联入口不是融合),rerank 用通用 LLM 而非专用 cross-encoder(单位成本与一致性都不如 bge/cohere 类 reranker)。为其辩护的事实是规模:KOL 池是千级(索引 ~1000+ 条),在这个量级 hybrid/RRF 的增益有限,而我们的工程护栏(预算闸、失败降级、rerank 只动展示分不污染召回分、全程审计字段)比多数教程级 hybrid 实现成熟。结论:**检索技术栈落后一档,工程纪律在线;若池规模上到万级,补稀疏召回+RRF 是明确的下一步**。

### 四、开源 influencer/marketing 工具对照

**业界现状(GitHub 实查)。** `influencer-marketing` topic 下星数最高的是 Claude Code 营销技能包(约 2.3k stars)与营销 agent 技能集(约 500 stars)——都是**提示词/技能层,不是平台**;NoxInfluencer 官方也只开源了技能包(创作者发现/尽调/联系方式)。平台类仓库(InfluencerFlow、HypeIt、Influencer-marketplace、Influencer_Brand-Network)全部是 demo/训练营项目量级(个位数到几十 star,无生产化痕迹);最接近生产的 OpenOutreach 是 LinkedIn B2B 外联工具,不做创作者营销。**结论:该品类没有成熟开源平台,由 CreatorIQ/Upfluence/Modash 等闭源 SaaS 主导。**

**我们的位置(已核实的链路)。** 本仓库是一条端到端自托管链:发现与去重(`profile_discovery.py` + `pool_merge.dedupe_enrolled_pool_row`)→ 向量召回与文本搜索(见上节)→ 视频深度分析(`gemini_video.py` final_v1 管线,含上下文缓存)→ 履约闭环与推荐反馈(`vkpi_skill_runs`/recommendation_feedback 账本)→ Shopify 短链归因 → 全链预算/成本台账。其中 KOL 匹配的核心资产 viltrox_fit_score 是存储列且为写入红线(全代码库单一合法写点,skill/agent 层只读)。

**判词:开源可比集内领先,但需限定语境。** GitHub 上不存在与本仓库同深度(发现→分析→履约→归因→预算治理一体)的开源自托管平台,这一点成立;但它更多说明**这个品类的开源生态是荒地**,商业价值都锁在闭源 SaaS 里——"开源里领先"不等于超越商业产品。相对商业 SaaS,我们的结构性差距是全网创作者数据覆盖面(他们有亿级库),结构性优势是自有数据主权、与自家业务(预算/履约/归因)的深度耦合、以及零订阅成本。

### 总评

| 维度 | 判词 | 一句话 |
|---|---|---|
| Agent 编排 | 合理(理念局部领先,表达力落后) | 与 Anthropic/12-Factor 共识同向;驾照制度是好设计但未落码 |
| LLM 工程 | 合理 | 自研小 LiteLLM;预算治理独有,路由智能差一代 |
| RAG/检索 | 合理偏落后 | 缺稀疏召回+RRF+专用 reranker;当前规模够用 |
| 开源 influencer 平台 | 开源可比集内领先 | 赛道无对手,但赛道本身是开源荒地 |

诚实的总画像:这套系统的强项从来不是单点算法先进性(路由、检索均非 SOTA),而是**每一层都带预算闸、账本、降级与人审的工程纪律**——这恰是 2026 年业界从"自由 agent"回摆到"确定性 workflow"后最被强调的能力。最大的纸面与实物差距是驾照分级自治:设计在文档里,代码里还没有。

# 第九章 本地算力版(后续版本):验证与设计

> 需求:大部分计算搬到员工 Mac/Win 电脑本地跑,LLM API 走轮转,结果回传服务器;桌面端要稳定、安全。本章为**先验证后入册**的产物:四路并行验证(限额实查/真实负载/仓库存量/桌面方案),全部基于官方文档、真实账本与真实代码,验证通过后才写入。

## 一、总判定

**整体效率:可行,且不是靠猜**——四个验证互相咬合:

1. **一把 Gemini Tier1 key 稳撑 6~18 条视频深析线路**(TPM 瓶颈),全天封顶 RPD 10,000 条/日;我们历史峰值仅 186 条/日,**key 限额从来不是瓶颈,瓶颈是单机串行 worker 和网络**。

| # | 缺口 | 事实 | 最小补法 |

## 五、验证 D:Mac+Win 桌面端方案

**推荐栈一句话**:Tauri 2.x 壳(装包 ~8-10MB/内存 30-50MB,更新走 minisign 强制签名校验不可关闭)+ PyInstaller **onedir** 打包现有 Python runner 作 sidecar(逻辑全留 Python,壳只管托盘/状态/开关/日志)+ 静默更新(latest.json 放 R2,无车道运行时才更新)。Electron 落选:体积内存 10 倍级劣势,且 electron-updater Windows 签名校验模型弱(曾有绕过 RCE)。

**「key 不落地」的关键事实**:三家厂商的官方短时效 token(OpenAI ephemeral/Gemini ephemeral)都只覆盖实时语音场景,**批量文本/视频调用必须自建 broker**——现成方案就是 LiteLLM 网关虚拟 key(TTL/预算上限/模型白名单/`/key/block` 秒吊销)。最终形态 = 中心代理拓扑 + 短租约凭证纪律:

```
员工机壳启动 → 设备注册(设备指纹+员工账号)→ 中心 key-broker(LiteLLM /key/generate)
   签发虚拟 key:TTL 12-24h,$预算,模型白名单,绑定 device_id → runner 仅存内存,不落盘不进日志
LLM 调用:runner --HTTPS--> 我方墙外 LiteLLM 网关 --真 key(仅存网关)--> Gemini/Claude/OpenAI
   (中国员工机 LLM 链路免代理;只有 yt-dlp 下载仍需本机代理,--proxy 参数级注入)
媒体回传:runner --> 中心签发 R2 预签名 URL(15min TTL)--> 直传 R2,不占中心带宽
结果回传:直连中心 PG(pgbouncer+TLS,每机独立账号)——预算闸/幂等/台账自动生效
撤销:离职/失窃 → /key/block 秒生效;真厂商 key 永不出网关
```

**签名与分发成本**:macOS 必花 $99/年(Apple Developer + 公证,Sequoia 起未公证应用几乎装不了,P0);Windows 内部分发期 $0(IT 白名单/组策略放行 SmartScreen),对外期 OV 证书 ~$200-400/年(Azure Trusted Signing $9.99/月 仅限美/加/欧/英主体,中国公司不合规)。**稳定性五件套**:壳监督 sidecar 指数退避拉起 + sidecar 父死自杀;yt-dlp 分片续传 + R2 multipart 重试;本地 SQLite journal 断点恢复;Sentry 双端崩溃上报(壳 minidump + Python sdk);更新前 drain 队列、按 device_id 灰度。**一台 8-16GB 员工机现实并发 2-3 条下载车道**(下载吃带宽不吃 CPU,remux 近零 CPU;瓶颈=代理出口带宽),配 6~18 条/key 的 LLM 容量,5 台员工机即可把日吞吐从 186 条推向 1,000+ 条/日量级——届时约束回到预算闸,这正是想要的形态。
