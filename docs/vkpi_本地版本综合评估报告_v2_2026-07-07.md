## 4. 最重要的产品判断

V-KPI 不能再按“找 KOL”来定义。真正有竞争力的定义是:

> 从产品上市开始,系统评估市场信号、产品适配、地区机会、KOL/dealer/官方账号/自媒体/独立站路径,生成今日增长路线,并在执行后把结果回流成下一次更准的判断。

这个定位比 KOL 工具更强,原因有三点:

1. **你有品牌第一方执行数据。** 外部 KOL SaaS 很难知道产品节奏、样品库存、内部项目失败原因、dealer 推进、官方账号素材沉淀和真实执行阻塞。
2. **你能从 SKU 上市而不是达人搜索出发。** 增长大脑问的是“这个产品该在哪个市场、通过哪个渠道组合推出”,KOL 只是其中一个渠道。
3. **你已经有结果评估地基。** `forecast_log`、`gtm_outcomes`、`prediction_runs`、`prediction_evals` 方向正确,但必须让它们开始进真实结果。

## 5. 当前必须正视的五个硬问题

### 5.1 发布闸红,不能直接上云

当前 `verify.sh` 不是全绿。后端/前端主测试过了,但 hardening strict 和 line guard 失败。上云前至少要修:

- 4 个 silent exception 改为有日志的宽容失败。
- `GtmCommandPage.tsx` 拆到 1000 行以下,建议拆成 route header、global cards、preview form、materialize panel、learning panel。
- 修完后重跑 `bash scripts/verify.sh` 到全绿。

### 5.2 线上和本地不是同一个产品状态

本地领先线上 209 个提交,线上 migration 停在 209,本地 migration 到 221。当前线上不是“本地系统的线上版”,而是一个较旧的生产状态。任何上线判断都必须包含:

- migration 210-221 是否能按顺序 apply。
- `sha_aligned` 是否从 false 变 true。
- server/client/worker 是否同一个 build。
- 新账本是否存在且不破坏旧业务。

### 5.3 新市场大脑账本有表无水

本地 `vkpi_gtm_outcomes=0`, `vkpi_signal_ledger=0`, `vkpi_prediction_runs=0`, `vkpi_prediction_evals=0`。这意味着 Market Brain 现在主要是结构性就绪,不是结果性就绪。

第一目标不是做更漂亮的策略模拟器,而是让一个 SKU 的闭环结果写进账本。

### 5.4 旧预测流水有水但没人对答案

`vkpi_forecast_log=1656`,其中 `1654` pending。`refresh_forecast_outcomes` 现在有手动 HTTP 入口,代码注释也写了“每日 job 后续直调”。这是一条最容易立刻点火的学习链:

1. 每日 job 调 `refresh_forecast_outcomes`。
2. 把已满窗预测从 pending 判为 `hit_in_band/below/above`。
3. 每周 rollup 区间命中率。
4. 把 KOL 预测经验迁移到 W6 `prediction_runs/evals`。

### 5.5 本地算力不能急着上线

local worker 现在没有真实设备,且存在协议风险:本地租约只在 `payload.local_lease_id` 打标,主 `apify_jobs_worker` 认领 SQL 当前只看 `status='queued'`,没有排除 local lease 标记。Local Runner 上线前必须修双认领,否则主 worker 可能抢走本地任务。

### Gate B:W7 上云,但不开大自动化

目标:把本地新骨架安全推到线上,先读真数据,不直接让 agent 自动执行。

上线原则:

- 先备份 DB、代码、dist。
- `.env` 不随 rsync,必须人工补 env。
- migration 自动 apply 前确认 210-221 均 additive。
- `KOL_DISCOVERY_BUILDOUT` 首日建议关,避免搜索即深爬烧成本。
- manager guard 上线会收紧权限,需提前确认 GoAffPro 佣金/优惠码操作者角色。
- 上线后 health 必须显示 server/client/worker SHA aligned,`db_migration_max=221...`。

上线后只开放:

- Market Brain/GTM Command 读页面。
- `gtm-plan/preview`。
- materialize dry-run。
- manager 真落库。

暂不开:

- 外部大规模 crawling。
- 自动 LLM 成本任务。
- 无人审动作执行。
- local runner 实机派工。

### Gate C:一个 SKU 最小闭环

目标:证明系统能从建议走到结果,不是只生成报告。

推荐流程:

1. 选一个数据最完整的 SKU,例如 300W EVO / 85mm / 135mm。
2. 输入 SKU + 国家 + 预算。
3. 生成 GTM preview。
4. dry-run materialize。
5. manager 确认生成 `gtm_bet`。
6. 派发 3-5 个 action。
7. 人工执行并 mark done。
8. 写入 `vkpi_gtm_outcomes`。
9. 生成 `vkpi_prediction_evals`。
10. Learning Summary 展示“系统学到了什么”。

成功标准:

- 至少 1 个 SKU 有完整 `preview -> bet -> action -> outcome -> eval`。
- `prediction_runs/evals` 不再是 0。
- UI 能看到推荐、执行、复盘三段。

### Gate D:UI 从卡片页升级为指挥台

目标:把“聪明”藏在系统内部,界面只展示路线、动作、风险和复盘。

Market Brain 首页建议三层:

| 层 | 展示 |
|---|---|
| 今日增长路线 | SKU、国家、渠道组合、预算、推荐打法、风险、置信度 |
| 今日执行队列 | 找 KOL、补联系方式、催合作、观察项目、重试失败、dealer follow-up |
| 学习沉淀 | 本周有效内容风格、失效假设、复投对象、地区机会变化 |

动态不做装饰,只做状态:

- Signal Stream:新市场信号流。
- GTM Route Map:SKU 到地区/渠道/人群/动作路线。
- Bet Lifecycle Timeline:idea -> preview -> materialized -> assigned -> done -> verdict -> learned。
- Confidence Gauge:置信度和缺失数据。
- Health Strip:SHA、migration、worker、scheduler、成本预算。

前端工程第一批:

- keepPreviousData,切 tab 不清屏。
- apiFetch in-flight 去重 + TTL/SWR。
- row-flash 和 AnimatedNumber。
- LazyMotion 瘦身。
- `SettingsPage.tsx` 静态/动态导入冲突处理。
- dist PDF 大文件移出 public。

### Gate E:预测和推论点火

目标:从“建议生成”变为“预测可评估”。

立刻能做的四小刀:

1. `refresh_forecast_outcomes` 挂每日 job。
2. `forecast_log` 结果双写或映射到 W6 `prediction_runs/evals`。
3. 每周生成区间命中率、方向命中率、误差分布。
4. 建立一个经验分位数 baseline,先别急着上复杂模型。

推论结构:

| 层 | 作用 |
|---|---|
| 规则/数据质量 | 检查样本量、新鲜度、库存、履约、缺失字段 |
| 统计预测 | p10/p50/p90、方向判断、置信度 |
| 因果/实验 | 同类 SKU/渠道对照、小预算 holdout |
| LLM 归纳 | 评论/视频/Reddit 痛点总结,动作解释 |

原则:LLM 是归纳器和解释器,不是唯一预测器。

### Gate F:小组模式按 SKU launch squad 做

目标:从“个人任务系统”变成“产品上市作战小组”。

每个 SKU launch board 至少包含:

| 角色 | 责任 |
|---|---|
| Launch Owner | 对 SKU 上市结果负责 |
| Product Lead | 产品卖点、库存、节奏 |
| KOL Operator | 找人、联系、寄样、跟视频 |
| Dealer Operator | 地区经销商推进 |
| Content Analyst | 视频/评论/素材复盘 |
| Official Account Owner | 官方账号排期与复用 |
| Growth Analyst | 独立站/联盟/转化数据 |
| AI Agent | 建议、预警、草拟任务、复盘 |

不要先做聊天系统。先做:

- `owner_staff_id` + `owner_group_id`。
- due date/status/result。
- SKU board 三条 lane:KOL、Channel/Dealer、Content/Official。
- manager 审批队列。
- action 结果回流 outcome/eval。

### Gate G:本地算力后置,先受限

目标:让本地机器承担视频/评论/素材处理,但不碰业务决策。

适合本地:

- `yt-dlp` 拉公开视频/评论/字幕。
- `ffmpeg` 抽帧、转码、压缩。
- 视频深析前处理。
- 大文件缓存和上传。
- 评论/语言/相关性预筛。

不适合本地:

- 最终写业务决策。
- 自动外联。
- 修改预算/佣金/优惠码。
- 管理 LLM key。
- 暴露公网调度控制面。

MVP:

1. 设备注册。
2. capability heartbeat。
3. 云端 job lease。
4. 本地 runner 领取。
5. 上传 artifact。
6. 回传 result_ref。
7. Worker Devices Panel 展示状态。

前置硬门:先修双认领。

### 第 15-30 天:小组模式和外部信号

1. SKU launch squad board。
2. Action owner/group/due/result。
3. Reddit/YouTube comments/Google Trends 轻量入账到 `signal_ledger`。
4. local runner 注册一台设备,只跑视频/评论预处理。

| 时间 | 重点 | 成功标准 |
|---|---|---|

## 9. 完成后所处阶段

如果本报告里的路线完整完成,V-KPI 不再只是“KOL 工具”或“内部运营面板”,而是进入:

> P2G 产品上市增长大脑 Beta / 内部生产验证阶段

更精确地说,这是从 0 到 1 闭环验证完成、准备进入 1 到 N 复制的阶段。它还不是完全成熟的商业化 AI 增长平台,但已经具备内部生产级 Growth OS 的雏形。

| 完成范围 | 所处阶段 | 说明 |
|---|---|---|
| W6.5 修债完成,`verify.sh` 全绿 | 工程可发布阶段 | 代码具备安全发车条件,但还没有证明业务闭环 |
| 本地 219-221 上云,SHA/migration 对齐 | 云端新架构上线阶段 | 本地新能力与线上真实环境合体 |
| 1 个 SKU 跑通 `preview -> action -> outcome -> eval` | 最小闭环验证阶段 | 证明系统不是只会生成建议,而能进入结果账本 |
| 3 个 SKU 有真实 outcome/eval | P2G MVP 成立 | Market Brain 开始具备可复盘样本 |
| 10 个 SKU/活动有复盘和命中率 | 内部生产 Beta 成立 | 可以做内部周会、复盘、资源分配和策略校准 |
| KOL/dealer/官方账号/独立站/affiliate 都能推荐和复盘 | Market Brain v1 | 不再围绕 KOL 单点,而是围绕产品整体市场推动 |
| 能复制到第二品牌且有 org 隔离 | 商业化 SaaS/平台化准备阶段 | 需要多租户隔离、数据边界、权限和 outcome 污染防护 |

阶段判断的分水岭是 `outcome/eval`:

- 没有 `outcome/eval`,系统是“智能推荐系统原型”。
- 有 `outcome/eval` 但样本少,系统是“P2G MVP”。
- 有稳定 `outcome/eval`、命中率、误差、学习记录,系统才是“增长大脑 Beta”。
- 能跨品牌隔离复用,才进入“商业化平台准备阶段”。

完全成熟还需要三类证据:

1. 多品牌/多租户隔离成熟,尤其是 `org_id` 和读侧过滤。
2. 至少几十个 SKU/活动的 outcome/eval 样本。
3. 预测命中率、区间命中率、动作 ROI 能稳定展示,并能解释为什么加码、观察或停止。

所以 90 天目标完成后的准确定义是:

> 内部生产级 P2G Growth OS Beta,不是终局平台,但已经越过“工具/页面/原型”阶段。

## 10. 对外和对内定位

对外定位:

> Market Brain | P2G 产品上市增长大脑

对外一句话:

> 从产品上市开始,系统自动评估市场信号、渠道机会、KOL/dealer/内容/独立站路径,生成今日增长路线,并在执行后把结果回流成下一次更准的判断。

对内红线:

> 每个建议都必须能追溯证据、能被人审、能执行、能记录结果、能评估误差、能影响下一次推荐。

## 11. 最终判断

V-KPI 有机会,但机会来自闭环,不是来自页面数量。现在最值得放大的优势是“品牌第一方产品上市数据 + 内部执行链 + 结果评估账本”。竞品平台可以很强地找 KOL、做社媒监听、做 campaign 报表,但它们很难同时拥有 Viltrox 的产品节奏、库存、样品、项目履约、官方账号素材、dealer 状态、联盟链接和内部 Action Inbox。

当前不能过度乐观。系统还不是已验证的市场预测大脑,因为新 GTM outcome/eval/signal/prediction 账本没有真实流水。也不能悲观。代码地基、权限闸、测试文化、页面入口、预测流水和行动池都已经存在。

最正确的下一步是:

1. 先修 `verify.sh` 红灯。
2. 再把本地 219-221 能力上云。
3. 用一个 SKU 打穿真实闭环。
4. 让预测开始被结果校准。
5. 再做 UI 动态、小组模式、本地算力和 agent 放权。

硬结论:

> 如果继续按 KOL 工具做,竞争力会被平台化产品压低;如果按 P2G 产品上市增长大脑做,并且把 outcome/eval 跑起来,V-KPI 有机会形成别人短期难复制的内部增长操作系统。
