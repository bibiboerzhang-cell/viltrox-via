## 2. 真正的缺口:结果回收(数据问题,不是代码问题)

实测血液状态:
```
vkpi_gtm_outcomes   = 0      ← 空
vkpi_prediction_evals = 0    ← 空
vkpi_prediction_runs = 18    ← 有水(baseline 日基线)
vkpi_forecast_log   = 1654 pending / 2 已裁决
gtm_bet             = 20 (1 executed / 1 approved / 18 suggested)
```

**为什么机器开着却不出 outcome?** 因为链条卡在「结果回收」这一环,而且是物理卡点:
1. 20 条 bet 里 18 条还是 suggested(没人审批 → 没执行 → 没到期 → 没裁决 → 没 outcome);
2. 就算审批执行了,`spawn_due_verdicts` 只在 bet 的 `review_at` **到期**才生成裁决任务——默认 30 天窗;
3. 1654 条 forecast pending 要被评估,需要**视频真的发出去、真有播放量**才能填 `actual_result`。

**结论:缺的不是代码,是「真实执行结果」。** 没有真人发内容、没有真 GMV,`actual_result` 就永远是空的。这是运营/数据问题。

## 4. 最小可落地闭环(下一步就做这个)

```
300W EVO → 美国 → 技术评测型 KOL → 生成 10 个行动 → 人审执行
  → 7 天后回收曝光/互动/失败原因 → 写入 outcome → 生成 eval → 下次推荐调整
```

### 两条路径(取决于能不能真执行)

**路径 A：真实闭环(需上云 + 真人执行)**
- 上云 W7 → 选 300W EVO/US → preview → materialize 3-5 条 action → 真员工执行发内容 → **短 review 窗**(7天而非30天)让裁决尽快到期 → outcome/eval 落账 → 学习卡非空。
- 这是唯一能产生**真实业务结果**的路径,但依赖上云 + 真人操作 7 天。

**路径 B：机器验证闭环(本地立刻可做,证明管线不出真结果)**
- 用库里现有 20 条 bet,选一条走完全链:approve → mark-done → 手录一份模拟的 actual_result(曝光/互动)→ 缩短 review 窗强制 spawn 裁决 → 人工裁决写 outcome → 触发 prediction eval。
- **产出**:outcomes/evals 从 0 变非 0,**证明管线端到端能跑**——这样上云真执行时,我们已经确信机器是通的,只等真数据灌进去。
- 代价:注入的是模拟结果,须标记为 `machinery_smoke` 并可清理,不污染真实学习统计。

**建议**:先做路径 B(本地半天,证明血液能循环),再上云做路径 A(真数据流过)。
