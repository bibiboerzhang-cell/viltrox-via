# V-KPI KOL Pool 顶配方案(给 Jianbo)

> 基于 8 路代码/数据库测绘 + 4 路隐性需求分析 + 4 路业界顶配对标的合成。凡未读到代码直接证据的判断标「(推测)」;凡 V-KPI 已落地的明确写「已有」。本方案不触碰 `viltrox_fit_score` 唯一写点 `pool.py:892`,不改 `rule_v0` 冻结公式。

## 1. 现状一句话总评

**V-KPI 已经能「抓到号、算出分、排出序、做出真实的内容级视觉分析、生成双语外联草稿、起草合同」——内核扎实甚至有独家护城河;但它几乎无法回答营销人真正的四个问题:「这个号能不能用(假粉/新鲜度)、是不是同一个人(去重)、怎么联系(email 0%)、它的分到底代表对哪条产品线契合(fit 语义塌方)」,而最终「拿一份可外联清单走人」这个最高频产出动作,因为 email 全空 + 导出不覆盖新池 + 收藏页是死胡同,目前根本走不通。**

被严重低估的真实强项(不要重复造轮子):语义向量召回(Qdrant 1536维真召回)、统一智能入口三模式、`plan_text_query` 自然语言→英文检索词规划、Gemini 6 层视频分析(429 条 + scene_timeline 99.8%)、合同生成/抽取/履约字段、Shopify/Amazon 归因底座、双语 AI 外联草稿。

最致命的系统性风险:**「已评分(scored 999)」被当成「可信/可用」**——实测约半数行 ER/avg_views 为 NULL、50 行恰好是 15.0 的纯 platform 基线、1012/1142 来自历史 Excel 导入。营销人按 fit_score 排序选号,会系统性偏向「高粉(含买粉)但与产品/垂类不对口」的号。

## 2. 隐性需求与规则约束清单(去重合并,按优先级)

### P0 — 止血与产出阻断(不做,系统对营销人基本不可用 / 有钱坑)

**P0-1 · 联系方式 0% = 外联产出链总开关关闭**
- 是什么:`email` / `other_contacts_json` 全表 0% 填充,`_normalize_item` 只被动取 Apify 几乎不含的 `publicEmail`(`pool_common.py:710`)。
- 为什么:`outreach_draft` 已能生成漂亮的双语话术,但没有收件人地址 = 空对空;`eleven_dimensions` block3 的 `contact_reachability_score` 因此恒为 0。**这是 P0 里的 P0,应最先解决数据源而非 UI。**
- 当前状态:草稿生成器 + 读写端 + 前端 `CopyEmailButton` 全就绪,唯独喂不到数据。
- 建议:补「公开商务邮箱」抓取管线(YouTube about/链接树、IG 商务资料、profile bio)。**严格合规边界:只取创作者公开声明的商务邮箱,不做全网正则爬邮箱**(见 P0-合规)。

**P0-2 · fit_score 几乎不含 Viltrox 适配语义,退化为「粉丝量×ER」函数**
- 是什么:唯一适配信号 `product_score` 上限仅 15 分(15% 权重),依赖 `primary_topic`(实测 0/1142 全空),只能靠 bio 子串命中;`brief` 永远硬编码 `{product_name:'Viltrox lens', category:'camera lens'}`(`pool.py:902`)。
- 为什么:Jianbo 看到的「契合分」回答不了「这个 KOL 适合推我哪条产品线(镜头 / 550pro 监视器 / Z1pro 闪光灯)」,也不分垂类(汽车/赛车/美食/婚礼/商业/旅行)。
- 当前状态:rule_v0 公式真跑、999 行真有分,但语义被硬编码 brief + 空 `primary_topic` 架空。
- 建议:**rule_v0 冻结不动**。改在「输入层 + 独立维度层」解决:(a) 让 `enrich_item` 的 brief 按目标产品线参数化(传不同 `product_name/category`,这不改公式只改入参,需确认是否算「写点改动」——保守做法是把产品线适配做成**独立影子分/独立维度列**不进 fit_score);(b) 把已算但未用的 `eleven_dimensions` block4(`industry_clusters.json` 15 桶 + SKU `product_fit`)透出为可筛可排的「产品线/垂类适配」标签。

**P0-3 · 假粉 / 假互动 / 受众真实性零检测——fit 反把刷量号排前面**
- 是什么:全仓 grep 零命中 `fake_follower`/`audience_credibility`/异常检测。`audience_score = min(25, followers/20000)` 给高粉号(含买粉)满分。
- 为什么:Viltrox 真金白银投放,最大钱坑是高粉低质号,系统当前主动把它们排到前面 = 直接预算损失。
- 当前状态:完全缺失。但 `real_er`(播放分母 ER)vs 生产 ER(粉丝分母 ER)的巨大背离能侧面暴露买粉——只是口径不可比、覆盖仅 8%、无 flag 落库。
- 建议:即便无第三方 API(HypeAuditor/Modash),先用现有数据做**规则离群**:followers 极高但 avg_views/ER 极低、ER 对同量级 peer 的 z-score 离群 → 产出「疑似刷量」flag(独立列,**不进 fit_score**)+ 人工复核清单。

**P0-4 · 去重半空壳 + 触达历史不回流 = 重复入池/重复触达**
- 是什么:`duplicate_of_id` 列建了(migration 109)**零读写=死列**;`vkpi_kol_pool_aliases` 0 行;去重只剩 `UNIQUE(platform,handle)` 撞库,`profile_basics._execute_insert` 还是裸 INSERT 无 ON CONFLICT(撞约束直接 IntegrityError 记 error)。
- 为什么:同一人的 YouTube+IG+TikTok 三个号是三条独立记录、各自打分/召回/收藏;批量外联会对同一人重复发邮件,损害品牌专业度。
- 当前状态:去重列+索引在但零使用;`history_match` 仅落库前用,漏判即重复入库。
- 建议:激活 `duplicate_of_id`,在 list/recall/收藏/项目/导出**全链统一过滤 `duplicate_of_id IS NULL`**(半接会造成读写不一致);触达历史回流 pool(已被谁/何时触达)。

**P0-5 · 导出不覆盖新池/收藏,My KOL 是只读死胡同**
- 是什么:`export_jobs._rows` 的 7 类里无 favorites,且 `export_type='kols'` 读的是 **legacy `kols` 表**而非 1142 行 `vkpi_kol_pool`;前端导出按钮硬编码 `reportType='weekly'`;My KOL 页 grep export/outreach 零命中。
- 为什么:营销人最高频的产出动作=导一份 KOL 名单进 CRM/给团队,目前 KOL Pool/收藏/项目名单全导不出,只能复制截图(PII 离境不留痕)。
- 当前状态:导出引擎(CSV/XLSX/PDF + 落盘 + `audit.log_export(contains_pii)` + 7天过期)完全可复用,只缺 3 个 `export_type` 分支 + 前端入口。**工作量 S,价值极高。**
- 建议:补 `favorites` / `project_kols` / `vkpi_kol_pool` 三个 export_type,前端在 My KOL/项目页加唯一合规导出入口。

**P0-6 · 规避中文 KOL:数据层不可信,且口径本身需 Jianbo 拍板**
- 是什么:`language` 列 0% 且全链无写入路径;唯一过滤在召回层 `_country_is_mainland`(只排大陆、放行 TW/HK)+ `_looks_chinese`(只看 display_name/handle 的 ≥2 汉字,**bio 不看**);`enrich_item`/`backfill`/`import` 写库时完全不看国别语言;`kol_ops.py /search/platform` 同步发现入口**完全旁路**中文过滤(后门通道)。
- 为什么:纯英文运营的出海中国号(大量真实存在)稳定漏过;Jianbo 误以为「已规避中文」实则裸通道。
- 当前状态:负向排中文在召回层真生效但判据弱;正向「英语市场」判定完全缺失。
- 建议(**两件事**):
  - (1) 工程:把过滤从「仅召回层」扩到「同步发现入口 + 写入层 + 导出/外联层」;`douyin` 从 `SUPPORTED_DISCOVERY_PLATFORMS` **代码层硬移除**,不再靠运维不配 env 兜底。
  - (2) **业务口径必须 Jianbo 成文拍板**(当前是工程师的隐性默认):① 大陆 CN 一定排;② 台湾/香港排不排?③ 华语但常驻海外做英文内容的创作者排不排?④ 判定优先级建议 = 内容语言/字幕语言 > display_name+handle 汉字 > country。**强烈建议把负向「按国籍排中国人」改写为正向「英语内容创作者筛选」**——后者既更准(覆盖非英语欧洲/日韩号),也规避了「按国籍排除」在合同/外联/导出中出现时的地域歧视声誉风险。

**P0-合规 · email 富化上线即从空列变 PII 收割管线**
- 是什么:面向英语/欧美创作者,GDPR/CCPA/CAN-SPAM/PECR 适用;`outreach_draft` 生成的 `message_en` 零合规元素(无身份披露、无退订)。
- 为什么:抓取自然人邮箱长期存储 + 用于外联是最敏感的处理,且当前无收割来源白名单、无列级访问审计、无外联合规模板。
- 当前状态:列+UI+导入读取已就位(将启用),合规门禁完全缺失。
- 建议:email 列接通前作为**放行前置条件**:① 只收公开商务邮箱白名单来源;② 列级访问审计 + 脱敏展示;③ 外联模板强制含发件人身份披露 + 退订选项;④ 禁止抓来邮箱直接群发。

**P1-2 · creator/reviewer 类型分类器后端无实现 + 覆盖 30% + 分数退化失效**

- 建议:为各产品线补 query 模板;`industry_clusters.json` 已有 lighting/wedding/travel 桶,接到产品召回。

**P1-4 · 画像置信度不可见 + 数据新鲜度无管理**

### P2 — 体验与向顶配靠拢

**P2-1 · 召回零多样性 = 每批头部恒定**
- 是什么:`profile_recall` 全文无 MMR/diversity/rerank/shuffle,embedding 确定 + 排序确定 + type_boost 退化 → 排序≈纯向量序;quota 硬上限不回补(creator 桶不足时名额浪费,returned_count 远小于 limit);两条调用入口权重还不一致(discovery 0.7/0.3 vs router 0.85/0.15)。
- 为什么:营销人反复搜同垂类只见固定 7+3,长尾永远沉底,误判「池子就这些」。
- 建议:加一层 MMR/主题打散/轻量随机扰动(**S 级即可缓解**);统一两入口权重;quota 加 backfill 回补。

**P2-2 · 前后端 URL/文字分流判据不一致 + 「平台识别到但不支持」无专门提示**
- 是什么:前端 `detectMode` 只要 hostname 含点就判 url(不校验空格/ASCII/CJK/已知域),后端 `_looks_like_url` 要求无空白+纯 ASCII host+命中已知域;facebook/twitter/x/bilibili/douyin 进 url 分支但 `classify_url` 因 `SUPPORTED_PLATFORMS` 只认 yt/ig/tt 全降 unknown,前端只给「无法识别 URL」。
- 为什么:所幸 `run()` 一律传 `mode:auto` 由后端定夺**不会真分错**,但按钮文案误导;粘贴 Facebook/B站链接会以为系统坏了。
- 建议:对齐前端预判判据;为「平台识别到但未接入」加专门文案(区别于「链接坏了」)。

**P2-3 · keyframe_qa 视频二审是死代码 + ROI 闭环未串通**
- keyframe_qa:analyzer+worker 都有完整实现,但**无生产入队路径**,429 条 final_v1 零 QA 覆盖,marketing_value 纠偏从未运行,且硬限 YouTube(IG/TikTok 拿不到)。TikTok profile 代表视频分析整条跳过(known issue)。
- ROI:`sales_attributions.kol_id` 指向 legacy `kols` 表,与 `vkpi_kol_pool` 主键不通,ROI 归不回新池;发现主链 Apify 花费**不入账**;final_v1 约 41% 失败(277 条 `last_error_category=NULL` 未分类)浪费成本无汇总。
- 建议:接通 keyframe_qa 入队(或明确砍掉死代码);解决 `kols ↔ vkpi_kol_pool` 身份映射后做单 KOL/单项目 ROI;final_v1 失败分类补全。

**P2-合规-成本 · 发现主链 Apify 花费是预算黑洞**
- 是什么:用户天天用的「全网发现→`discover_new_creators`」走 `account_scan_service._run_actor`,**既不 check_budget 也不 record_cost**;`provider:apify` 40 USD 上限只对用户基本不点的批量刷新路径生效;即便已接的路径也是「纯事后记账、不预检、不拦截」(`run.usageTotalUsd` 跑完才有)。
- 为什么:每点一次「全网发现」都在 40 USD 上限之外烧钱且无人知晓,月底账单远超 ledger,无法归因。
- 建议:发现主链接入 `record_cost` + `provider:apify` 预检(把记账从纯事后改为含 preflight);发现路径加 `since` 增量游标(当前每次全量重抓重烧 Apify)。

# 完整性批判:KOL Pool 方案的缺口清单

## A. 三层证据明确支持、但方案完全遗漏的需求

**A-1 · DSAR/被遗忘权级联删除——方案 P0/P1 全程未列为工作项,只在风险红线第3条一笔带过**
- 证据:隐性(合规 lens)P0 明确「KOL 数据进得来出不去」,一个 KOL 散落 ≥8 表(vkpi_kol_pool / video_evidence / profile_deep / analysis_cache / index_entries + Qdrant point / llm_deep_analysis_results / R2 10227 资产 / export 文件),当前唯一 delete 是 legacy 内部硬删 + remove_favorite,无主体级联删除路径。
- 缺口:方案把它降格成「风险提醒第3条④」,既无工作项、无闸映射、无预估。若 email 富化(P0-1)真上线,DSAR 删除是 email 上线的合规前置条件之一,却没和 P0-合规绑定。这是 P0 合规清单里漏掉的一项硬门禁。

**A-2 · R2 真人头像/视频的留存策略——完全未提**
- 证据:隐性(合规)P0,R2 实测 image/cached=10020(可识别人脸)+ video/cached=207(真人原片完整副本),留存控制只有容量 GC + 168h 失败封锁,无「分析完成后 N 天删原片、只留缩略图/结论」的时间/主体维度策略;且原片是他人作品完整副本,叠加版权/ToS 风险。
- 缺口:方案合规红线只讲了「Apify+yt-dlp 是封号暴露面」,但没讲「囤在自己桶里的 10020 张人脸 + 207 段原片本身就是隐私留存 + 版权债」。这是独立于抓取动作的存储侧合规缺口,方案零覆盖。

**A-3 · PII 列级访问控制 / scope 归属键 NULL 导致的越权——未提**
- 证据:隐性(合规)P2 + 收藏测绘 implicit_assumptions:scope.project_filter 自陈「33 个项目归属键全 NULL、存量 75% 双归属 NULL」,非 admin 员工对非 restricted 项目读写全放行;叠加 email 上线 = 全员可访问自然人 PII,不满足 GDPR 访问最小化。
- 缺口:方案 P0-合规只讲「列级访问审计 + 脱敏展示」,但没讲底层 scope 权限闸本身因归属键 NULL 已经失效。email 脱敏审计建立在一个已经漏的权限模型上——这是审计的前置依赖,方案没指出。

**A-4 · 多 worker 横向扩展会突破进程内 Gemini QPS 锁——放量风险未提**
- 证据:任务-护栏测绘 + 成本 lens 风险末条:_gemini_qps_lock 是进程内锁(GEMINI_QPS=0.05),多 worker 进程间不共享,放量时若加 worker 进程,Gemini 调用频率与成本可能失控超出 provider:gemini 60 的预期节奏。
- 缺口:方案 P1「放量面板」只讲调 env/cap/解封 blocked,但放量最自然的动作就是加 worker 进程,而这会绕过 QPS 节流。放量方案缺一条「横向扩进程前必须先把 QPS 锁改成跨进程(DB/Redis)」的前置约束。

**A-5 · monthly spend 与 caps.current_spend 两套账本漂移——成本红线漏写**
- 证据:任务-护栏测绘 gap 末条 + 成本 lens:llm_gateway 的 monthly 闸用 SUM(vkpi_llm_calls.cost_cents),而 provider/scope 闸用 caps.current_spend(record_cost 累加),两者可能漂移(record_cost 失败/漏调即偏)。enforce 同时依赖这两个不同账本。
- 缺口:方案成本红线第4条只提了 NUMERIC(10,4) 亚美分偏差,但没提「两套真值源本身就可能对不上」。亚美分是精度问题,双账本是一致性问题,是两个独立的 enforce 可信度风险。

## B. 证据支持、方案弱写或定性偏轻(漏掉关键事实)

**B-1 · `_looks_like_url` 的 TLD 兜底会误吞紧凑英文关键词——方案 P2-2 漏了这条**

- 缺口:方案 P2-2 只讲了前后端判据不一致 + 「平台识别到但不支持」无提示,漏了这条「想当关键词搜的英文短语被误判成 URL」的真实误吞。营销人会问:为什么我搜某个词它当链接处理了。

**C-2 · 「P0-5 工作量 S」与「P0-1 email 是 P0 中的 P0」并存,但 P0 出口标准要求两者都完成**
- 方案 P0 出口标准:「能导出一份含联系方式+fit+垂类+友商+触达状态的 CSV,且无重复人、无中文号」。
- 矛盾点:这个出口标准把 P0-1(email,L,且依赖合规门禁先定)、P0-4(去重激活,L)、P0-5(导出,S)、P1-1(友商扩表,M,且在 P1 阶段)全捆进 P0 出口。但 P1-1 的友商关系明确在 P1 阶段才做,「含友商」的 P0 出口无法达成。出口标准混入了 P1 交付物,阶段边界不自洽。要么把「含友商」从 P0 出口移除,要么把友商扩表提前——方案没对齐。

**C-3 · 数据质量体检报告标「工作量 —(只读 DB)」,但它依赖的口径(可信门槛、纯基线定义)尚未拍板**
- 方案把「数据质量体检报告」列为 P0、工作量 S/只读。但隐性(数据质量)rules_constraints 明确要求先定义「数据可用最低门槛(ER 与 avg_views 至少一项非空、sample_n>=N)」「fit_score=15 基线≠评估过的低分」这些口径。
- 张力:报告本身只读不假,但报告要呈现的「真实可用率」分母/阈值是业务口径,未拍板就出报告会得到一个无共识基准的数字。方案应把「可信门槛口径」像规则①一样列成 Jianbo 决策项,而不是默认工程自定。

## D. 营销人(Jianbo)会问、但方案没答的问题

**D-1 · 「我搜 IG 创作者和搜 YouTube 创作者,质量为什么不一样?」**
方案没告诉 Jianbo:发现链在 YT(streamers/youtube-scraper,真增量)、TT(free-tiktok-scraper)、IG(hashtag-scraper,单 hashtag 语义退化)、TikTok profile 代表视频整条跳过(known issue)上的能力是**严重不对等**的。Jianbo 会以为「系统对三平台一视同仁」,实则 IG 召回质量结构性偏低、TikTok 拿不到 profile 视频分析。这个平台间不对等没有出现在任何一节。

**D-2 · 「这份外联清单导出去之后,删不删得掉?数据放在哪、谁能看?」**
对一个面向欧美创作者的营销负责人,导出 PII 后的去向台账(谁/何时/导了谁/发往何处)、能否应创作者要求删除——隐性合规 lens 明确列为 expected_output(PII 离境台账 + DSAR),但方案的产出清单 13 项里没有「PII 离境台账」「DSAR 删除入口」。Jianbo 真被欧盟创作者问到时,系统给不出。

**D-3 · 「同一个人我已经联系过了,系统会不会让我/同事再发一次?」**
方案 P0-4 讲了去重 + 触达回流的工程实现,但产出清单和出口标准里,「触达历史可见(已被谁/何时触达)」只在去重条目里附带,没有独立成「外联清单必含触达状态列且全链可见」的验收点。而 B-4 的归属错配会让这个状态在按员工分发时失真。Jianbo 最怕的重复打扰,方案的验收没有正面兜住。

**D-4 · 「创作者的粉丝是不是我要的英语市场?」**
方案 P0-3 做了假粉规则离群,P0-6 做了创作者侧语言过滤,但**受众侧**(粉丝地理/语言分布)在方案里只出现在 P2「受众人口学/地理/语言洞察(XL)」最末。顶配对标明确指出:决定「英语市场」硬规则能否真正落地的关键是**受众语言/地理**,不是创作者国籍。方案把规则①的真正可信判据(受众侧)放到了最后的 XL,却用 P0-6 的创作者侧负向排中文当主力——这等于告诉 Jianbo「已规避中文/已锁英语市场」,但其实只过滤了创作者本人、没看粉丝。这个「创作者英文 ≠ 受众是英语市场」的根本局限,方案没向 Jianbo 点破。

**D-5 · 「fit 分能不能告诉我这个号适合哪条产品线?」——方案答了「会做」,但没答「rule_v0 冻结下,产品线适配永远进不了那个排序分」**
方案 P0-2/P1 反复说做成独立维度/影子分。但 Jianbo 的实际使用动作是「按 fit_score 排序选号」。独立维度不进 fit_score = 他按 fit 排序时产品线适配仍然不影响顺序,只能当二次筛选标签看。方案没诚实告诉 Jianbo:**在 rule_v0 冻结的约束下,「按契合度排序」和「按产品线契合排序」是两个永远无法合并的排序**,他得接受「先按 fit 排、再按产品线标签筛」的两步操作,而不是一个统一的「产品线契合分」排序。这是冻结红线带来的、对最高频动作的体验代价,被方案的「独立维度」措辞模糊掉了。

## 一句话总结缺口

方案在**工程缺口**层面已近乎穷尽(P0-P2 覆盖了测绘的几乎所有 gap),真正系统性遗漏集中在三处:**(1) 合规的「出口侧」**——DSAR 级联删除、R2 留存策略、PII 离境台账、scope 越权,方案只覆盖了「入口侧」(email 抓取合规)而漏了「数据如何安全离开/删除」;**(2) 受众侧 vs 创作者侧的根本区别**——规则①(英语市场)的真正判据在受众语言/地理,被排到最末的 XL,而方案用创作者侧负向排中文当主力却暗示已达标;**(3) 平台间能力不对等**(IG hashtag 退化 / TikTok profile 跳过 / 三平台增量不一)从未作为一个独立认知摆给 Jianbo。此外有两处必须修的自相矛盾:**P0-2 的 brief 参数化在逻辑上必然撞冻结红线(应删除该选项)**,以及 **P0 出口标准混入了 P1 的友商交付物(阶段不自洽)**。
