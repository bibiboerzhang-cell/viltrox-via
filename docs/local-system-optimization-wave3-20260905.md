# 第三批：可审阅计划、预算校验与受控 LLM 路线

日期：2026-09-05。用户要求给出进阶方案并继续执行，允许使用 LLM 预算。

## 建议与优先顺序

更好的方向不是继续堆看板，而是把现有 AI Marketing Brain 收敛成一个以项目和证据为中心的工作流：先理解需求，说明为何选这些人和方向，再落实资源、审批、任务与回执。

| 阶段 | 做什么 | 为什么 | 验收与放量条件 |
| --- | --- | --- | --- |
| 本轮：计划可读、数字可信 | 将原始 JSON 转为摘要、预算、节奏、候选、依据风险；补金额、配比和候选身份校验 | 用户能直接核对计划，不依赖读代码；LLM 不能自行决定金额和身份 | 合成正反例、前后端回归、浏览器展示与无额外调用 |
| 下一步：受控 LLM 质量验证 | 先复用已配置且获准的精确模型通道；规则作基线，固定合成需求集验证结构、引用、约束和理由 | 模型生成成功不等于结果适用；强模型或多模型不天然提高质量 | 精确通道与预算 scope 就绪；逐例记录耗时、用量、失败和质量；未核验不能提升为生产就绪 |
| 再下一步：项目工作台 | 在现有项目内串起机会、候选、Brief、样品、档期、审批、任务与结果 | 减少跨页面重复理解和跟进；让每一步有负责人及完成定义 | 先一个产品族、一个市场的真实样板；真实终态、交付和费用可追踪 |
| 验收后：有节制的自动化 | 来源增量刷新、冷却、异常队列、复盘反馈；按平台逐个扩大 | 避免同时扩量带来的重复抓取、未知费用与噪声 | 每个平台的凭据、权限、数据质量、费用、停止条件和连续任务观察独立通过 |

不承诺凭一次技术修复直接达到 80–90 分、提高转化率或固定倍数提速；先取代表性任务的端到端基线，再比较冷/热缓存、并发、p50/p95、失败率和真实成本。测试运行时间不是用户操作响应时间。

## 展示上的进阶

1. **默认看结论与下一步**：规划目标、预算、缺口、需人审事项；原始 JSON 保留在技术详情，不删除证据。
2. **按需展开依据**：每个候选的匹配与排除理由、引用、日期与范围。当前合同没有逐人理由，必须明确“待补”，不能由 fit 分数或 tier 编造。
3. **同页看状态与费用**：建议、批准、入队、终态分别展示；规划金额与模型实际费用分开，未知不能显示为免费。
4. **逐步引入项目时间线**：负责人、前置依赖、样品和交付节点；目前仍是相对周次的建议，不把默认四周当已确认档期。

本轮不重写导航、不迁移到新框架、不引入向量库或微服务；先复用现有 Skill Studio、KOL、项目和 Action Inbox。

## 本轮已经实现的代码

### 计划与预算

- 预算输入拒绝布尔、浮点分、负值、非有限值和超 JSON 精度范围；允许十进制整数字符串。未知预算输出 null，而不是 0。
- 规则分配采用整数权重的最大余数法，同余时按原顺序；有效预算各桶合计精确等于预算。
- 模型预算需唯一用途、整数金额且总额不超预算；合法少分配保留未分配额，比例由程序重算；异常整组回规则并保留提示。
- 模型候选仅能引用本次候选池，展示身份从服务端材料恢复；梯队唯一、份额有限且合计在 1 的绝对误差 1e-9 内。异常字段按字段回退，不让标量或畸形数据使页面崩溃。
- 缺输入时不调用模型；一旦调用过，即使失败或回退规则，模型成本仍标为 unknown。
- 新的预算诊断和 model_cost 是附加字段；原 planning_readiness 始终未批准、不可执行。

### 页面

新增结构化草案，显示摘要、预算分配及余款、相对周次、候选分组、内容线索和风险。旧数据或异常字段保守显示待核验，币种不推断。JSON 默认折叠；其他技能保持原展示。新增 65 条英文翻译。

### LLM 小额探针

- 默认预算检查要求本次 scope 已配置；未配置时零预约、零外调，不能依靠全局月余额隐式放行。
- 下一次预约前检查“已核验费用＋本次估算”是否超本轮限制。
- 总期限从入口计入准备耗时，预约后与外调前重新检查。未外调但已标 provider_started 的预约可能不能释放，明确保留待核对，不假称释放。
- 缺失或双零用量不按已知零费用结算；迟到但有已知费用的成功回执先对账，再报告超时。

以上是局部保护，不保证供应商账单绝对封顶；HTTP 重定向仍可能增加物理请求。adapter 对原始用量完整性与历史账本零占位的全链路迁移仍未解决。

## LLM 预算授权与本轮实测边界

用户已允许 LLM 预算。本轮先拟定一次固定非敏感连通探针，1 次 adapter 调用、16 输出 token、20 秒、0.10 美元本轮限制；未提高全局月预算或每日抓取额度。

本轮只读检查不是供应商连通或生成质量证明：

- 当前选定绑定为 `openai/gpt-5.6-luna`，凭据、注册定价、transport 可用；价格是本地注册表估算，未作为供应商账单核验。
- zero-I/O dry-run 的单次估算为 0.000024 美元；实际供应商调用 0。
- PostgreSQL READ ONLY 预检显示：当前七个任务绑定与既有生产 operator ACK 的交集为 0，所选模型 signed readiness 未通过。
- `cron:campaign_plan_canary` 与既有 `cron:vkpi_stage1_model_canary` 均未配置。
- Stage1 的 plan-bound 临时授权与生产 operator ACK/signed readiness 是不同机制。未冒充生产就绪，也未新建 scope 或签启 live 临时授权。
- 只读连接已 rollback/close。第一份探针收尾有未 await 异步关闭函数的警告；随后 scope 检查正确 await 关闭，无额外调用或写入。

因此本轮实际模型调用 **0**，没有真实供应商消费证据；不能把本地月度余额当作任务 scope 已授权。下一步应单独确认拟启用的评测 scope、精确通道、金额和终止条件，再做真实小额验收。

建议的启用顺序：先配置仅用于一次连通检查的独立小额 scope，再生成绑定当前精确计划的本地探针授权；只验证固定非敏感探针、记录实际用量与未知费用。成功仅能证明该次连通，不自动打开生产生成、更不启用定时任务。随后才用合成资料做 campaign_plan 质量对照，保留 record=False 与独立供应商回执，最后进入有负责人验收的真实样板。
