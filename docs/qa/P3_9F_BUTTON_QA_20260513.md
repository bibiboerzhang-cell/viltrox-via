## Skipped In This Pass

These buttons should be tested in controlled endpoint QA because they change state, trigger downloads, send messages, or may call LLM/API providers:

- 全局: `退出`
- 全局: `导出 PDF`, `导出 CSV`, `生成周报`
- 项目跟进: `完成当前步，进入下一步`, `计入快递 / 推广费`
- 数据分析: `关闭抓取`, `刷新该账号`
- 系统设置: provider `检测`, `发送邀请`, `保存 SKU`, `保存评论告警阈值`, `保存个人偏好`, `保存通知配置`, platform `开启/关闭/保存当前平台限制`
- 报表导出: `按当天真实动作生成 Ledger`

## Findings

1. Settings page is the biggest UI overload: 83 buttons on one page, including repeated platform controls and smoke-created staff rows.
2. API status table previously exposed key prefixes in the UI. P3.9E masked this to only `已配置/未配置`.
3. Deep link navigation is now available via `#projects`, `#settings`, `#dataAnalysis`, etc., which makes browser QA possible even when the sidebar is hidden on narrow viewports.
4. Button inventory alone is not enough. Remaining work must test backend endpoints and resulting database state for risky buttons.
5. `client_matches_server=false` is still a release-risk signal and should be closed before handoff/demo.

## Recommended Next Round

P3.9G endpoint-level QA for risky buttons:

1. Export PDF/CSV: verify actual file/download endpoint, no fake success.
2. Generate weekly report: verify endpoint, LLM gateway/fallback, and report content provenance.
3. Data analysis refresh account: verify one account refresh with real provider status and no duplicate rows.
4. Settings platform save: verify one platform budget/limits update and audit record.
5. Project stage/cost: verify stage transition, evidence attachment, cost ledger write, and project detail drawer reflects it.

Acceptance for P3.9G: each tested button has a route, endpoint, expected DB table write/read, and pass/fail evidence.
