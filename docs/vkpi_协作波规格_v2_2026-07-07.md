## C2 团队协作图（纯读）

**目标**：一张只读全景图——组 × 成员 × 共享资产 × 在线态 × 在管 KOL，让管理层一眼看清「谁在哪个组、组里共享了什么、谁在线、谁在跟哪些 KOL」。

**数据源全齐（零新表）**：本节纯聚合已有表，无任何写入。

| 维度 | 来源 |
| --- | --- |
| 组 × 成员 | `vkpi_staff_groups.member_ids`（jsonb bigint 数组） |
| 成员展示名/邮箱 | `staff` JOIN `users`（`COALESCE(u.name, u.email)`） |
| 在线态 | `users.last_seen_at`（`> now() - INTERVAL '5 minutes'` = 在线，镜像 `staff.list_members::user_online`） |
| 共享资产（项目） | `vkpi_project_members WHERE shared_via_group_id = <origin>` |
| 共享资产（KOL） | `vkpi_kol_pool_members WHERE shared_via_group_id = <origin>` |
| 共享资产（活动，C3 落地后） | `vkpi_event_members WHERE shared_via_group_id = <origin>` |
| 在管 KOL claims | `vkpi_kol_pool` claim 归属（按成员 staff_id 聚合，只读计数） |

### 数据模型
无。纯读。`origin_id` 复用 `service._group_origin_id(group_id)`（`grp_<ms>` → BIGINT 后缀）。

### 迁移
无。

### 端点（新增，纯读）
`GET /api/vkpi/staff-groups/collab-map`（新 handler，宿主 `vkpi_staff_groups.py`）
- 权限：`require_tab("vkpi", "read")`；非管理层按 `list_groups` 同款收口（只见自己所在组，X4-LOW 口径），管理层看全部。
- 返回结构：
  ```json

      {
        "id": "grp_1718500000000",
        "name": "...",
        "members": [
  ```

## C3 共享互通：Events 组共享

**目标**：把「组共享」范式从 项目/KOL 扩到 Events——`ShareModal` / `NewEventModal` 加「选分组」，组成员展开进 `team_ids`（建活动时）或 `vkpi_event_members`（分享时），**镜像现有幂等展开范式**。

**两条落点（都要，各覆盖一个入口）**：

### 落点 A — NewEventModal 建活动时选组（前端展平，最小改动）
建活动时选一个分组 → 该组 `member_ids` 在前端展平进 `teamIds` 再提交。

- 数据模型：无。`team_ids` 已是 bigint 数组，展平即写。
- 迁移：无。
- 端点：复用 `POST /api/vkpi/events`（`create_event` 已吃 `team_ids`）。
- 前端入口：`NewEventModal.tsx` 现有 `teamOptions`（个人多选）旁加一个「分组」下拉；选中组把 `group.member_ids` 并入 `teamIds`（去重，`ownerId` 保持 `teamIds[0]`）。经 `staffGroups-api` 拉组列表。
- 语义：这是**一次性快照**（建时把当时组员拍进 `team_ids`），后续改组成员不回溯——符合「活动团队 = 当时拉的人」的直觉；不需要 origin 追踪。

### 落点 B — ShareModal 分享给组（后端幂等展开，镜像 projects/kols）
`ShareModal(kind='event')` 加「分享给分组」→ 后端把组成员展开进 `vkpi_event_members`（标 `shared_via_group_id`），改组即重算。

- **数据模型**：`vkpi_event_members` 加一列 `shared_via_group_id BIGINT`（镜像 160/161）。
- **迁移**（新，号 ≥ 225，例 `225_vkpi_event_members_group_origin.sql`）：
  ```sql

  --   镜像 160/161:让 staff_groups/service.py 把"组级 shared_event_ids x 组成员"展开成真
  --   vkpi_event_members 行;service.list_events / scope.assert_event_access 据此放行(零改 scope)。
  --   ADDITIVE:只加一列 + 部分索引,绝不改 vkpi_events/staff;只加宽读,不放开写。
  ```

  - 在 `create_group` / `update_group` / `_set_members` / `delete_group` 里，紧挨现有两个 `_recompute_group_shared_*` 调用旁**再加一行** `_recompute_group_shared_events(...)`。

## C4 智能路由：Inbox 组归属

**目标**：Action Inbox 加 `owner_group_id`（additive）+ `list_inbox` 支持按组过滤 + 管理层按组看视图 = 后续 C4 智能路由（按组自动派单）的落点前提。

### 数据模型
`vkpi_action_inbox` 加一列 `owner_group_id BIGINT`（`NULL` = 无组归属，保持现有 `owner_staff_id` 语义）。与现有 `owner_staff_id`（个人级，`NULL`=公司级）并存：
- `owner_staff_id` 非空 → 个人任务（现状不变）。
- `owner_group_id` 非空 → 组任务（组内成员可见）。
- 两者都空 → 公司级（仅管理层可见，现状不变）。

### 迁移（新，号 ≥ 226，例 `226_vkpi_action_inbox_owner_group.sql`）
```sql
-- 226(C4): 给 vkpi_action_inbox 加 owner_group_id(组归属,为按组路由/按组看视图铺路)。
--   additive、幂等;NULL=无组归属(保持现有 owner_staff_id 语义);零触 viltrox_fit_score。
ALTER TABLE vkpi_action_inbox
    ADD COLUMN IF NOT EXISTS owner_group_id BIGINT;
CREATE INDEX IF NOT EXISTS idx_action_inbox_owner_group
    ON vkpi_action_inbox (owner_group_id)
    WHERE owner_group_id IS NOT NULL;
```
`owner_group_id` 存 `_group_origin_id` 口径的 BIGINT（`grp_<ms>` 后缀），与 `shared_via_group_id` 同源，便于 JOIN 回 `vkpi_staff_groups`。回滚见 `226_..._down.sql`。

### 端点（改造 `list_inbox`）
`backend/app/domains/actions/inbox.py::list_inbox` 加可选 `group_id: int | None = None` 参数：
- 管理层（`scope.can_view_all`）：
  - 传 `group_id` → `WHERE owner_group_id = ?`（按组看视图）。
  - 不传 → 现状全局（不变）。
- 成员（非管理层）：现有 `owner_staff_id = ?` 分支**加宽**为「自己的个人任务 OR 自己所在组的组任务」：
  ```sql
  (owner_staff_id = ?  OR  owner_group_id IN (<成员所在组的 origin_id 列表>))
  ```
  组列表来自「`member_ids` 含自己」的 `vkpi_staff_groups`，映射成 `origin_id`（复用 `_group_origin_id`，可在 `staff_groups/service.py` 加只读 helper `member_group_origin_ids(staff)`，镜像 `scope.member_shared_project_ids`）。
- SELECT 列表补 `owner_group_id`;返回 `scope` 字段扩展为 `all` / `own+group` / `group`。
- 路由 `list_inbox` 端点（宿主 inbox 路由）加 `group_id` query 透传。
- **persist 侧**：`persist_suggestions` / `generate_daily_action_inbox` 的 INSERT 补 `owner_group_id`（producer 产物可选带 `owner_group_id`，缺省 `NULL`——不改现有 producer 行为，只留位）。

### 前端入口
- Inbox 页顶部加「按组筛选」下拉（管理层可见，选项来自 `collab-map` / `list_groups`）；成员端默认已含自己组任务，无需操作。

### 工作量

- **新缺口：`owner_group_id` 列 + 组过滤分支 + `member_group_origin_ids` helper。** 智能路由（自动把建议派给某组）是本列之上的后续刀，本波只铺列 + 可见性。

## 死字段激活

两个已存能读、无人消费的死字段：`kpi_goal`（组目标）、`reminder_rule`（提醒规则）。16 人规模下，**通知 feed + 前端铃铛比 IM 性价比高**（异步收件 vs 实时聊天，实现轻、噪音低）。

### D1 — `kpi_goal` 接 Dashboard 组聚合

**现状**：`vkpi_staff_groups.permissions_json.kpi_goal` 仅默认值 + service 读写，无 Dashboard 消费。

- **数据模型**：无新表。读 `permissions.kpi_goal`（文本目标，如 "本月 GMV 50 万"）+ 组 `member_ids`。
- **迁移**：无。
- **端点**（新，纯读）：`GET /api/vkpi/dashboard-staff/group-summary?group_id=<id>`（宿主 `vkpi_dashboard_staff.py`）：
  - 取组 `member_ids` → 复用现有 dashboard 聚合器（`backend/app/domains/dashboard/`，如 `summary.py` 的 4 聚合吃 `effective_staff_id`）**按组成员求和**，返回 `{kpi_goal, aggregated: {gmv, videos, ...}, progress}`。
  - 权限：管理层看任意组;成员看自己所在组（`list_groups` 同款收口）。
  - **不碰 v6_fit**;只聚合既有 dashboard 只读指标。
- **前端入口**：Cockpit 组卡片/协作图（C2）上加「组目标 vs 实际」进度条，数据来自 `group-summary`。
- **验收**：给组设 `kpi_goal` → `group-summary` 回该目标 + 组成员指标求和;数值与逐个成员 dashboard 求和一致。`--strict` EXIT=0。
- **工作量**：1 只读端点（复用现有聚合器）+ 前端进度条（约半天–1 天）。**地基复用度：高**（复用 dashboard 聚合），**新缺口仅：组聚合端点**。

### D2 — `reminder_rule` 接每日 job + 新建通知 feed

**现状**：`reminder_rule` 两处都是死字段——
1. `vkpi_staff_groups.permissions_json.reminder_rule`（组级，service 读写、无人消费）;
2. `vkpi_collab_settings.reminder_rule`（迁移 174，per-resource，`ShareModal` 存 / `dashboard_staff` + `my_kol` 读，**无 job 消费**）。

激活 = 每日 job 扫 `reminder_rule` → 命中则往**新通知 feed 表**写一条 → 前端铃铛读未读。

- **数据模型**（新表 `vkpi_notifications`）：
  ```sql
  -- 227(D2): 通知收件流(bell feed)。每日 reminder job 命中即写一行;前端铃铛读未读。
  --   additive、隔离表;不碰 vkpi_events/projects/staff/viltrox_fit_score/rule_v0。
  CREATE TABLE IF NOT EXISTS vkpi_notifications (
      id            BIGSERIAL   PRIMARY KEY,
      recipient_staff_id BIGINT NOT NULL REFERENCES staff(id) ON DELETE CASCADE,
      kind          TEXT        NOT NULL DEFAULT 'reminder',   -- reminder|mention|share|system
      title         TEXT        NOT NULL DEFAULT '',
      body          TEXT        NOT NULL DEFAULT '',
      source_kind   TEXT        NOT NULL DEFAULT '',            -- project|event|group|''
      source_id     TEXT        NOT NULL DEFAULT '',
      dedupe_key    TEXT        NOT NULL UNIQUE,                -- 日重算幂等(kind:source:date)
      read_at       TIMESTAMPTZ NULL,
      created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
  );
  CREATE INDEX IF NOT EXISTS idx_vkpi_notifications_recipient
      ON vkpi_notifications (recipient_staff_id, read_at, created_at DESC);
  ```
  `dedupe_key` 保证一天同一提醒只发一条（幂等）。回滚 `227_..._down.sql`。
- **迁移**（新，号 ≥ 227）：上表 + 228 注册 scheduler_task（镜像 141 尾部 `INSERT INTO scheduler_tasks`）：
  ```sql
  -- 228(D2): 注册每日提醒 job(默认 enabled=FALSE,运营显式开启才真跑)。
  INSERT INTO scheduler_tasks (task_key, label, risk_level)
  VALUES ('daily_reminder_scan', '每日协作提醒扫描(reminder_rule 到通知)', 'low')
  ON CONFLICT (task_key) DO NOTHING;
  ```
- **每日 job（新)**：`backend/app/domains/actions/`（或 `alerts/`）加 `reminder_scan.py::run_daily_reminder_scan(conn)`：
  - 扫 `vkpi_collab_settings WHERE reminder_rule <> ''` + `vkpi_staff_groups permissions.reminder_rule <> ''`。
  - **v1 规则解析先做最小可用**：把 `reminder_rule` 当「触发条件文本」，v1 只支持简单口径（如「临近 `end_date`」「N 天无更新」），命中即对相关 recipient（组成员 / 资源共享成员）幂等 `INSERT INTO vkpi_notifications ... ON CONFLICT (dedupe_key) DO NOTHING`。复杂 DSL 留后。
  - 由线上 scheduler（`daily_reminder_scan` timer/循环）触发，镜像 `daily_action_inbox_generate`。**禁裸 print;禁 silent except**（producer 容错要 `logger.warning(..., exc_info=True)`）。
- **端点**（新，通知 feed）：宿主新路由 `vkpi_notifications.py`：
  - `GET /api/vkpi/notifications?unread=1&limit=50` → 当前 staff 的通知（`recipient_staff_id = effective`，scope 收口）。
  - `POST /api/vkpi/notifications/{id}/read` → 置 `read_at`。
  - `POST /api/vkpi/notifications/read-all` → 全标已读。
  - 权限 `require_tab("vkpi","read"/"write")`;只读/写自己的通知（`assert_staff_access` 口径）。
- **前端入口**：顶栏铃铛组件（复用在线态心跳 `/me` 的轮询节奏，60s 拉未读计数）；点开抽屉列未读，点条跳 `source`。宿主 `frontend/src/components/vkpi/`（顶栏/cockpit 外壳）。
- **验收**：
  - 给某 project 设 `reminder_rule`（临近 end_date 口径），手工跑 `run_daily_reminder_scan` → 相关共享成员 `vkpi_notifications` 各一行;再跑一次不重复（`dedupe_key` 幂等）。
  - `GET /notifications?unread=1` 回该行;`POST /{id}/read` 后未读数减 1。
  - `scheduler_tasks` 有 `daily_reminder_scan` 行（默认 `enabled=FALSE`，不自动跑）。
  - `scripts/check_repo_hardening.py --strict` EXIT=0；`.venv/bin/pytest` 新用例绿。
- **工作量**：1 表迁移 + 1 scheduler 注册迁移 + 1 job 模块（含 v1 规则解析）+ 1 通知路由（3 端点）+ 前端铃铛（约 2–3 天，含 v1 规则设计）。
- **地基复用度：中**（scheduler_tasks 注册范式、心跳轮询节奏、scope 收口可复用）;**新缺口最多：通知表 + job + feed 端点 + 铃铛 UI 全新建**。
