## 1. 总结论

客观判断:有机会,但机会不在“再做一个 KOL 平台”。如果只围绕 KOL 搜索、达人库、视频分析,竞争会越来越弱,因为 CreatorIQ、Traackr、Upfluence、Brandwatch 这些平台已经覆盖了 KOL 发现、社媒监听、活动管理、ROI 报告等标准功能。V-KPI 真正有机会冲出来的方向是“品牌方自己的产品上市增长大脑”:从产品上市开始,把产品、地区、人群、KOL、dealer、官方账号、自媒体、独立站、库存、项目履约和结果回流统一到一个闭环里。

当前本地版本已经不是空想。代码里已经有 Market Brain/GTM Command 页面、GTM preview、Action Inbox materialize、manager 权限闸、signal ledger、prediction runs/evals 迁移、local worker 设备表、skill runs、agent/orchestrator/event ledger 等骨架。问题也很硬:本地有新脑骨架但真实结果数据没喂进去,线上有真实业务数据但还停在旧迁移和旧代码。现在还不能说“系统已经会预测市场”,只能说“系统具备开始形成预测闭环的地基”。

一句话评价:

> 本地代码已经接近“可点火的智能增长操作系统”,但还不是“已验证的市场大脑”。下一步不是继续堆页面,而是把线上真实数据、结果账本、预测评估、行动回流接成一个最小闭环。

## 4. 目前最大的优势

### 4.1 你有品牌方第一方闭环数据

大多数 KOL 平台强在“找人”和“报表”,弱在品牌内部真实执行链:

- 产品准备情况
- 库存/样品/发货
- 项目履约
- KOL 视频证据
- 官方账号表现
- dealer/独立站/联盟佣金
- 成本与执行结果
- 内部 Action Inbox

V-KPI 目前已经把不少内部链路放在同一个系统里。这是比外部 KOL SaaS 更有价值的壁垒。CreatorIQ/Traackr/Upfluence 能告诉品牌找谁、活动怎样,但它们通常不知道你的产品真实节奏、样品库存、内部项目失败原因、dealer 推进状态、官方账号素材沉淀和真实执行阻塞。

### 4.2 你不是从“达人维度”出发,而是能从“产品上市维度”出发

未来真正值钱的问题不是:

> 这个 KOL 好不好?

而是:

> 这个产品现在该在哪个国家、通过哪类人、用哪类内容、配哪类 dealer/自媒体/独立站路径推出,今天应该先做哪一步?

这就是 P2G 大脑。KOL 只是渠道之一,不是系统中心。

### 4.3 你已经开始做“可被评估的建议”

本地已有 `prediction_runs`、`prediction_evals`、`gtm_outcomes` 方向,这是关键。很多平台会给推荐,但不持续记录:

- 当时推荐了什么
- 基于哪些证据
- 置信度是多少
- 预估曝光/回复/转化是多少
- 实际结果怎样
- 错在哪
- 下一次权重怎么改

只要这条线跑起来,V-KPI 才会真正变聪明。

## 5. 最刺耳但必须承认的问题

### 5.1 现在还不是“市场预测大脑”

原因很简单:本地 `vkpi_prediction_runs=0`,`vkpi_prediction_evals=0`,`vkpi_gtm_outcomes=0`,`vkpi_signal_ledger=0`。没有预测运行记录、没有预测评估、没有结果校准、没有统一外部信号账本,就不能说系统已经具备真实预测能力。

当前只能说:

- 已经有预测账本结构
- 已经有 GTM preview 和 action materialize
- 已经有证据聚合入口
- 已经有成为预测系统的地基

但离“能被市场验证的预测系统”还差真实结果回流。

### 5.2 线上真实数据和本地新能力割裂

线上有 1353 个 KOL、473 个 action、20 个 dealer、5 个 GoAffPro link、3.8 万官方账号 post metrics,但线上代码还停在 migration 209。  
本地有 219-221 新账本,但本地 dealer/goaffpro/outcome/signal/prediction 基本空。

这会导致一个危险错觉:看本地代码觉得很先进,看线上数据又觉得很真实,但两者没有合体前,产品并没有形成真实线上闭环。

### 5.3 UI 还没把“聪明”藏到系统里

你提到“很多东西不能展示出来,聪明和市场感知要深深在系统内处理”。这是对的。当前 GTM/Market Brain 页面如果继续堆很多解释性卡片,会显得像分析报告,不是增长大脑。

最终用户应该看到的是:

- 清晰路线图
- 预判结论
- 推荐方针
- 今天要做的任务
- 需要人工确认的风险
- 做完后的复盘结果

不要把所有中间推理、模型特征、采集细节、权重计算全部暴露出来。系统内部保存证据链,界面只展示“可行动结论 + 可追溯原因”。

### 5.4 还没有形成跨渠道闭环

闭环不能只围绕 KOL。产品市场推动至少要覆盖:

| 渠道 | 需要回答 |
|---|---|
| KOL | 找谁、给什么内容、什么时候合作、复投谁 |
| Dealer | 给哪个地区/经销商、配什么卖点、如何跟进 |
| 官方账号 | 发什么内容、复用哪类素材、哪个主题加码 |
| 自媒体/PR | 哪些话题值得写、哪个媒体角度更容易传播 |
| 独立站/Shopify | 入口、落地页、转化、优惠码、AOV |
| Affiliate | 佣金策略、链接归因、长期合作 |
| Amazon/BH/平台评论 | 用户痛点、竞品短板、产品文案修正 |
| Reddit/YouTube comments | 真实讨论、情绪变化、早期需求信号 |

如果系统最终仍然只说“找 10 个 KOL”,那不是增长大脑,只是 KOL 工作台。

## 6. UI 优化方向

### 6.1 对标结论

参考平台:

- Linear:强调速度、低噪音、AI workflow 与人协作。
- Vercel Dashboard:强调性能、项目状态、部署/运行健康、快速切换。
- Amplitude:用 dashboard 把相关指标放在一起,让团队做周会/复盘。
- Retool:强调生产级 AI workflow、权限、人工审批、审计轨迹。

V-KPI 不应该做成营销官网式页面,也不应该做成全是大卡片的“展示屏”。它应该像一个运营指挥台:密度高、信息清楚、动作入口明确、状态实时变化。

### 6.2 Market Brain 页面应该从“五卡片”升级为“三层”

第一层:今日增长路线

- 今日主推 SKU
- 推荐国家/地区
- 推荐渠道组合:KOL / dealer / official / affiliate / independent site
- 推荐动作数量
- 风险等级
- 置信度
- 下一次复盘时间

第二层:执行队列

- 待找 KOL
- 待补联系方式
- 待催合作
- 待发货/待样品
- 待观察项目
- 待重试失败内容
- 待 dealer follow-up
- 待复盘

第三层:系统学习

- 本周新学到的产品-人群匹配
- 哪些内容风格有效
- 哪些地区不值得继续烧
- 哪些 KOL/dealer 值得复投
- 哪些假设被市场打脸

### 6.3 动态体验建议

要“更多动态”,但不是装饰动画,而是让状态变化可感知:

| 动态组件 | 作用 |
|---|---|
| Signal Stream | 实时滚动:Reddit/YouTube/官方账号/项目/竞品新信号 |
| GTM Route Map | SKU 到国家、渠道、人群、动作的动态路线图 |
| Bet Lifecycle Timeline | idea -> preview -> materialized -> assigned -> done -> verdict -> learned |
| Confidence Gauge | 展示置信度和缺失数据,不要展示复杂模型权重 |
| Action Pulse | 今日新增/完成/超时/重试任务的实时计数 |
| Learning Delta | 本周系统权重变化:哪些信号变重要、哪些变弱 |
| Health Strip | build SHA、worker、scheduler、数据新鲜度、成本预算 |

已有 `framer-motion`、`lucide-react`、`three` 依赖,不需要再引入重库。重点是把动效绑定到真实状态,而不是做视觉花活。

| P0 | GTM/Market Brain 顶部加一条“增长路线图”:SKU、市场、渠道组合、今日动作、风险 |

## 7. 本地算力是否要加入

结论:要加,但不能成为当前主线的第一个阻塞点。

本地算力适合做:

- `yt-dlp` 拉取公开视频/评论/字幕
- `ffmpeg` 抽帧、转码、压缩
- 视频深析前处理
- 批量素材指纹/去重
- 本地缓存和上传
- 一些轻量 embedding/preprocess
- 大文件处理和低成本离线任务

本地算力不应该做:

- 最终业务决策写库
- 未审批的自动外联
- 预算/佣金/优惠码修改
- LLM key 管理
- 线上唯一调度源
- 暴露到公网的 Ray/worker 控制面

### 7.1 当前代码地基

已有:

- `migrations/213_vkpi_worker_devices.sql`
- `backend/app/domains/local_workers/registry.py`
- `backend/app/domains/local_workers/dispatch_policy.py`
- `backend/app/api/routers/vkpi_local_worker_board.py`
- `frontend/src/components/vkpi/cockpit/components/WorkerDevicesPanel.tsx`

但本地 `vkpi_worker_devices=0`,说明真实设备注册、任务租约、回传链路没有跑起来。

### 7.2 MVP 建议

第一版不要直接上复杂分布式计算框架。先做 V-KPI Local Runner:

1. 设备登录并绑定 staff/org。
2. 上报 capability:`ffmpeg`,`yt-dlp`,`video_preprocess`,`comment_fetch`,`embedding_precompute`。
3. 云端生成 job lease。
4. 本地 runner 轮询领取任务。
5. 本地执行,生成 artifact。
6. 上传到 R2/云端。
7. 回写 `result_ref`,`duration_ms`,`error`,`device_id`。
8. 前端 Worker Devices Panel 展示 idle/running/failed/completed。

### 7.3 与 Ray/Temporal/Prefect 的关系

| 工具 | 适合什么 | V-KPI 当前建议 |
|---|---|---|
| Ray | 大规模 Python/AI 分布式计算、task/actor/object | 暂不作为公网 worker;只可在内网受控批处理后期考虑 |
| Temporal | 长时间、可恢复、可重试、有人审的业务工作流 | 适合未来 action/verdict/agent workflow,不是第一天替换现有 scheduler |
| Prefect | Python 数据管道、重试、缓存、事件自动化 | 可用于外部信号采集和数据质量管道,但先保留现有轻量 scheduler |
| 自研 lease runner | 低复杂度、本地视频/评论处理 | 当前最合适的 MVP |

Ray 很强,但如果暴露控制面会有安全风险。V-KPI 的本地算力第一版应该是“云端派工 + 本地受限执行 + 结果回传”,不是“把分布式集群暴露出去”。

## 8. 小组模式评估

当前系统已有一些小组/权限地基:

- staff/permission
- manager guard
- project assignments
- action owner/mark done
- KOL/project/share modal
- scheduler/settings 权限

但还不是“增长小组模式”。增长大脑需要按产品上市组织小组,不是按页面组织小组。

### 8.1 推荐的小组结构

每个 SKU launch 建一个 squad:

| 角色 | 责任 |
|---|---|
| Launch Owner | 对 SKU 上市结果负责,确认打法 |
| Product Lead | 提供产品卖点、库存、上市节奏 |
| KOL Operator | 找人、联系、寄样、跟视频 |
| Dealer Operator | 区域经销商推进、线下/渠道动作 |
| Content Analyst | 分析视频/评论/素材风格 |
| Official Account Owner | 官方账号排期、素材复用 |
| Growth Analyst | 看独立站/联盟/平台结果 |
| AI Agent | 只做建议、预警、草拟任务、复盘归纳 |

### 8.2 页面需要支持的协作方式

- 每个 GTM bet 必须有 owner。
- 每个 action 必须有 due date/status/result。
- 每个 SKU 有一个 launch board。
- 每个 board 有三条 lane:KOL、Channel/Dealer、Content/Official。
- manager 能看到风险和审批项,普通成员只看到自己的执行队列。
- agent 的建议必须可接受、拒绝、修改、延后。
- 所有执行结果进入 learning/outcome ledger。

### 8.3 不建议做的事

不要一开始做复杂组织架构、聊天系统、全套项目管理。V-KPI 小组模式的核心不是聊天,而是:

> 系统把产品上市拆成任务,每个任务有负责人,每个结果能回流,每个复盘能改进下一次推荐。

## 9. 智能体与推论系统

### 9.1 当前已有智能体地基

代码里已经有:

- `workflow_engine.py`
- `event_ledger.py`
- `skill_registry.py`
- `vkpi_skill_runs`
- `brain_acceptance`
- `prediction_ledger.py`
- `signal_ledger.py`
- `Action Inbox`
- `manager_guard`

这说明不是从零开始。真正要补的是“主循环”。

### 9.2 推荐智能体分工

不要搞一个万能 agent。推荐拆成 8 个角色,但用一个状态机管住:

| Agent/模块 | 输入 | 输出 |
|---|---|---|
| Signal Collector | 官方账号、KOL、项目、Reddit、评论、Trends、竞品 | 标准化 signal |
| Evidence Retriever | SKU/国家/人群/历史项目 | basis/source_state |
| Opportunity Scorer | 信号、历史结果、渠道数据 | 产品/地区/人群机会分 |
| Channel Allocator | KOL/dealer/official/affiliate/independent site | 渠道组合建议 |
| Risk Critic | 库存、履约、失败率、成本、数据缺口 | 风险和阻断项 |
| Action Writer | 推荐动作 | Action Inbox 草稿 |
| Human Approval Gate | manager/owner | approve/reject/edit |
| Verdict Learner | 执行结果 | outcome/eval/weight update |

关键原则:

- 开放式推理可以交给 agent。
- 固定流程必须由 workflow/state machine 管。
- 写库和外部动作必须有人审或权限闸。
- 每个建议必须带 `basis`,`confidence`,`missing_data`,`side_effects`,`source_state`。

### 9.3 推论工作如何完成

V-KPI 的推论不应该只靠 LLM。建议分四层:

第一层:规则和数据质量

- 数据新鲜度
- 样本量
- 是否缺库存/价格/dealer/link
- KOL 历史失败率
- 项目履约异常

第二层:统计预测

- SKU x country x channel 的曝光/回复/转化 baseline
- p10/p50/p90 区间
- 置信度和缺失数据惩罚
- 方向判断:加码/观察/停止

第三层:因果/实验

- 同类 SKU 在不同渠道的对照
- KOL 合作前后变化
- 官方账号内容主题变化后的表现
- dealer 地区差异
- 小预算 holdout

第四层:LLM 归纳

- 从评论/Reddit/YouTube comments 归纳痛点
- 从视频深析归纳内容风格
- 草拟动作说明
- 解释为什么推荐该打法

LLM 是解释器和归纳器,不是唯一的预测器。

### 9.4 预测账本最低标准

每次系统给建议,必须写:

| 字段 | 说明 |
|---|---|
| `run_id` | 一次预测唯一 ID |
| `product_sku` | 产品 |
| `market` | 国家/地区 |
| `channel` | KOL/dealer/official/affiliate/independent_site |
| `horizon_days` | 预测周期 |
| `p10/p50/p90` | 预测区间 |
| `confidence` | 置信度 |
| `basis` | 证据摘要 |
| `missing_data` | 缺什么 |
| `input_fingerprint` | 输入快照指纹 |
| `created_by` | system/agent/user |

结果回来后写:

| 字段 | 说明 |
|---|---|
| `actual_value` | 实际曝光/回复/转化/GMV |
| `error_abs/error_pct` | 误差 |
| `interval_hit` | 是否落在 p10-p90 |
| `direction_hit` | 方向是否判断对 |
| `calibrated_bucket` | 用于后续校准 |

如果没有这套评估,系统永远会“看起来聪明”,但不会真的变聪明。

## 11. 本地到线上推进方案

### P0:上线前安全闸

1. 清理或确认当前未跟踪文档。
2. 全量跑 `scripts/verify.sh` 或至少 backend pytest + frontend build。
3. 确认线上备份路径和回滚脚本。
4. 确认迁移 210-221 是否都能按顺序 apply。
5. 确认 `BUILD_GIT_SHA`、frontend client build、health `sha_aligned` 上线后必须一致。
6. 确认 manager guard 在生产账号下可用。

### P1:先把本地新骨架上线,不立即自动跑大动作

上线目标:

- 线上 migration 到 221。
- `/health` 显示 `db_migration_max=221...`。
- server/client/worker SHA aligned。
- Market Brain/GTM Command 页面可访问。
- GTM preview 可读线上真实数据。
- materialize 先 dry-run,真落库仅 manager。
- 不开启外部爬取和自动 LLM 成本任务。

### P2:用一个 SKU 做最小闭环

选一个产品,例如 300W EVO / 85mm / 135mm 中数据较完整的 SKU:

1. 输入 SKU + 国家 + 预算。
2. 生成 GTM preview。
3. dry-run materialize。
4. manager 确认生成 `gtm_bet`。
5. 人工执行 3-5 个 action。
6. mark done。
7. 写 `gtm_outcomes`。
8. 生成 `prediction_evals`。
9. Learning Summary 展示本周学到什么。

这一步比做 20 个页面更重要。

### P3:再打开自动化

只有当 P2 成功后,再逐步打开:

- due verdict scheduler
- GTM window refresh
- signal ingestion
- local worker video preprocess
- weekly learning summary
- external market radar

## 12. 30/60/90 天路线图

### 0-7 天:闭环点火

- 上线本地 W5/W6 到云端。
- 解决线上 SHA 不一致和 migration 209 滞后。
- Market Brain 页面接线上真实数据。
- 选 1 个 SKU 跑 preview -> materialize -> action -> done -> outcome -> eval。
- UI 顶部加“增长路线图”和 health strip。

成功标准:

- 线上 `sha_aligned=true`。
- `vkpi_signal_ledger`、`vkpi_prediction_runs`、`vkpi_prediction_evals`、`vkpi_gtm_outcomes` 表存在。
- 至少 1 个 SKU 有完整闭环记录。

### 14-30 天:产品上市小组和信号账本

- 建 SKU launch squad board。
- Action owner/due/result 标准化。
- 接 Reddit/YouTube comments/Google Trends 的只读入账试点。
- local worker MVP 注册一台设备,先做视频预处理/拉取。
- Learning Summary 从真实 outcome/eval 生成。

成功标准:

- 3 个 SKU 有 GTM bet 和 outcome。
- 每周学习记录不再是空。
- local worker 至少完成 10 个受限任务。

### 60 天:多渠道增长脑

- dealer/affiliate/official/independent site 进入同一个 opportunity board。
- 预测支持 p10/p50/p90 和 interval hit。
- manager 能看到“加码/观察/停止”建议。
- 建立 channel allocation:不同预算下 KOL/dealer/official/affiliate 的组合。

成功标准:

- 至少 3 个渠道产生 outcome。
- prediction eval 可计算方向命中率和区间命中率。
- 人工复盘能修改系统权重或规则。

### 90 天:可商业化雏形

- 形成稳定 P2G workflow。
- 支持多个产品 launch board。
- 建立权限/租户/数据隔离策略。
- 将 agent 从“建议生成”推进到“受控执行”:草拟任务、提醒、复盘、轻量自动化。
- 对外演示时强调“产品上市增长大脑”,不是“KOL 搜索工具”。

成功标准:

- 线上真实闭环稳定运行。
- 至少 10 个 SKU/活动产生可复盘 outcome。
- 系统能展示过去建议的命中率、误差、学习变化。

## 13. 推荐产品定位

不要把页面叫 KOL Brain。建议稳定为:

> Market Brain | P2G 产品上市增长大脑

对外一句话:

> 从产品上市开始,系统自动评估市场信号、渠道机会、KOL/dealer/内容/独立站路径,生成今日增长路线,并在执行后把结果回流成下一次更准的判断。

内部一句话:

> 每个建议都必须能追溯证据、能被人审、能执行、能记录结果、能评估误差、能影响下一次推荐。

## 14. 最终建议

下一步不要继续大范围扩功能。最优先的工作顺序:

1. 线上补齐本地代码和 219-221 迁移。
2. 用线上真实数据跑一个 SKU 的完整 GTM 闭环。
3. 补 `gtm_outcomes` 和 `prediction_evals` 的真实写入。
4. UI 从五卡片升级为“增长路线图 + 执行队列 + 学习沉淀”。
5. 外部信号只先接 Reddit/YouTube comments/Google Trends 的轻量入账。
6. local worker 做一个受限 runner,只处理视频/评论/素材,不碰业务决策。
7. 小组模式按 SKU launch squad 做,不要先做泛项目管理。
8. agent 先做建议和复盘,不要先做无人审自动执行。

硬结论:

> V-KPI 有机会,但不是因为别人没做 KOL 工具,而是因为你能把品牌方真实产品上市、内部履约、渠道执行和市场反馈接成闭环。现在最关键的不是更聪明的界面,而是真实结果账本和预测评估。没有 outcome/eval,系统永远只是像大脑;有了 outcome/eval,才会开始变成大脑。
