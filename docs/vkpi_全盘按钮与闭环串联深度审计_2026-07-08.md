## 1. 结论先说

当前本地版本已经能支撑“页面级可用性审计”:主导航能进入,核心页面能渲染,前后端编译和测试全绿。  
但如果按“每个按钮点下去都知道预期结果、写到哪里、谁接下一步、系统学到什么”的标准,现在还没有达到。

严苛结论:

- 页面壳、主导航、核心功能入口:可用。
- API 基础接受度:可用。
- 测试与 build 门禁:当前全绿。
- 按钮级治理:不足。
- 实时任务串联:有明确 403 断点。
- 智能闭环:仍未跑通,主要账本为空。

一句话:  
**现在是功能很多的强 Beta,不是按钮级可追责的增长操作系统。要升级成智能闭环,下一步要先做 Action Registry + Outcome Ledger + Button Telemetry,而不是继续堆页面。**

## 3. 浏览器发现的真实问题

### P0-1: SSE 实时流鉴权必然 403

浏览器网络错误:

```text
GET /api/admin/vkpi/progress/center/stream -> 403
GET /api/admin/vkpi/activity/stream        -> 403
```

原因:

- 前端认证主通道是 `localStorage` 里的 Bearer token。
- `useEventStreamOrPoll` 使用原生 `EventSource(streamUrl, { withCredentials: true })`。
- 原生 EventSource 不能携带 `Authorization` header。
- 后端 `/center/stream` 使用 `Depends(require_tab("vkpi", "read"))`。
- 浏览器没有 cookie session,所以 SSE 直接 403。

影响:

- 顶栏任务进度中心实时性断。
- Activity stream 实时性断。
- 前端会回退轮询,所以页面不白屏,但这是降级,不是实时闭环。
- 网络层会持续产生无效 403,误导运维。

修复方向:

1. 短期:对 SSE 关闭默认启用,检测 token auth 模式时直接走轮询。
2. 中期:用带 token 的短期 query token,例如 `/stream?sse_token=...`,后端专门校验一次性/短期 token。
3. 长期:改为 fetch streaming 或统一 cookie session,避免 EventSource 与 Bearer auth 冲突。

### P0-2: worker 离线,按钮到后台任务的链路不完整

`/health`:

```text
worker_heartbeat = 2026-07-03T11:44:31Z
worker_online    = false
```

这意味着:

- “补全中”
- “深析”
- “重试失败”
- “同步”
- “生成”
- “执行”

这些按钮即使前端能点,也可能只能入队,不能完成。

要做按钮全链路验收,必须同时跑:

```text
按钮点击 -> action/job 入队 -> worker claim -> worker done/failed -> UI 状态刷新 -> outcome/eval 写入
```

现在只证明到了“页面能点/接口能通”,没有证明后台能闭环。

## 4. 页面逐项严苛评价

状态: 可用。

- `稍后处理` 禁用态存在,但禁用原因不够显性。
- Dashboard 已经有 Action 影子,但没有统一 Button Action Registry。

### MY KOL

状态: 可用,数据丰富。  
风险:

- 官方账号、矩阵、内容层、导出、刷新混在一起。
- `导出收藏名单`、`刷新` 属于副作用按钮,需要明确结果落点。
- 当前 smoke test 有 act warning,异步刷新状态测试不够硬。

### KOL Pool

状态: 可用,真实数据。  
风险:

- 多个卡片显示“待补全/补全中”,但 worker 离线时这类状态会长期不落地。
- 搜索输入为空时按钮禁用是正确的。
- “补全中”卡片很多,需要后端任务状态和 UI 状态强绑定,否则用户会以为系统在工作。

## 5. 串联关系应该怎么补

目前很多按钮是“点了做事”,但不是“点了进入闭环”。  
目标链路应该统一成:

```text
Button Click
  -> Action Registry 记录按钮语义
  -> API endpoint
  -> Action Inbox / Job Ledger / Domain Ledger
  -> Worker / Scheduler / Human Review
  -> Result / Outcome
  -> Prediction Eval
  -> Learning Memory
  -> 下一次推荐权重变化
```

建议新增一个轻量按钮治理模型,不一定马上建复杂表,但前端至少要有 registry:

```ts
type ButtonActionKind =
  | "read_navigation"
  | "read_refresh"
  | "dry_run"
  | "write_db"
  | "enqueue_job"
  | "external_call"
  | "destructive";

type ButtonActionSpec = {
  actionId: string;
  label: string;
  page: string;
  kind: ButtonActionKind;
  endpoint?: string;
  expectedResult: string;
  resultSurface: string;
  ledger?: "action_inbox" | "job_ledger" | "gtm_outcomes" | "prediction_evals" | "audit_log";
  requiresConfirm?: boolean;
};
```

前端按钮至少加:

```text
data-action-id="gtm.command.generate_preview"
data-action-kind="dry_run"
```

后端结果至少统一返回:

```json
{
  "ok": true,
  "action_id": "gtm.command.generate_preview",
  "side_effect": "none|db_write|job_enqueued|external_call",
  "ledger_ref": {"table": "...", "id": "..."},
  "next_status_url": "...",
  "human_message": "..."
}
```

这样以后才能自动跑“每个按钮点完应该看到什么”。

1. 修 SSE 鉴权:

   - 更新 README/本地验收步骤。

4. 跑通最小 GTM 闭环:
   - 一个 SKU。
   - 一个国家。
   - 一个 action。
   - 人审执行。
   - 写 `vkpi_gtm_outcomes`。

1. 建前端 `buttonActionRegistry.ts`。

## 8. 最终判断

如果只是问“页面能不能跑”:  
**能跑,而且当前本地验证门禁全绿。**

如果问“每个按钮有没有确定结果、能否串到闭环”:  
**还不够。现在缺的是按钮级治理和 outcome/eval 账本。**

如果问“智能大脑下一步要做什么”:  
**不要先加更多页面,先让一个按钮从点击到学习完整闭环。**

最小验收目标:

```text
GTM Command 输入 SKU
  -> 生成作战预览
  -> 物化 Action Inbox
  -> 人审执行
  -> 标记结果
  -> 写 vkpi_gtm_outcomes
  -> 写 vkpi_prediction_evals
```
